# Monologue Coach — Frontend Documentation

Everything that runs in the browser: the pages, the Monologues list, Daily Practice on a
monologue (the checklist, its timer, and the tools of each step), a take's full analysis,
the General Practice screen (recording, uploading, results, coaching, history, feedback
and calibration), and what is saved in the browser. Start with
[DOCUMENTATION.md](DOCUMENTATION.md) for the big picture and the glossary. The Python side
is in [DOCUMENTATION_BACKEND.md](DOCUMENTATION_BACKEND.md).

Why `features/practice/`, `features/monologue/` and `features/general/`, and not everything
in `components/`: each feature keeps its own logic, storage and screens together in one
folder. `components/` is only for things several features share.

The three lean on each other in one direction. `general/` knows how to send a recording,
follow its job and show a result, and knows nothing about the other two. `monologue/`
builds its screens out of those pieces. `practice/` owns the routine and puts
`monologue/`'s tools under its steps. Two files left in Phase 8: `MonologuePractice.tsx`
(the old Monologue screen) and `ReferenceLibrary.tsx` (its menu of references), both in
`general/components/`.

The development server runs on port **1234** by default (`npm run dev`). A fixed port
matters more than usual here: the browser keeps saved data per address, so a changing port
would hide the checklist's history (decision F16).

In Next.js the folder name is the address: `src/app/practice/page.tsx` becomes `/practice`.
The page files are deliberately tiny. They only pick which feature to show; the real work is
in `features/`.

`src/app/layout.tsx` wraps every page. It draws the header with the app name and the

## 4. How the frontend talks to the backend

- All backend addresses are built by `src/lib/api.ts`. For example
  `apiUrl("/api/health")` gives `http://localhost:4321/api/health`.
- The base address defaults to `http://localhost:4321`. To change it, create
  `frontend/.env.local` containing `NEXT_PUBLIC_API_BASE_URL=http://localhost:9000`.
- The browser calls the backend directly; requests do not pass through Next.js
  (decision G2 in the main document).
- The home page asks `GET /api/health` once when it loads and shows one of four messages:
  checking, running, running but the database check failed, or not reachable.
- Everything the monologue screens and General Practice ask of the backend goes through
  one object, in `src/features/general/api.ts`:

| Function | Request | Used for |
| --- | --- | --- |
| `getHealth` | `GET /api/health` | The notice when the API, worker, speech model or AI model is missing |
| `getOptions` | `GET /api/analysis-options` | Profiles, languages and upload limits for the form |
| `submitAnalysis` | `POST /api/analyses` | Sending a recording: a take; a take of a monologue, with `monologueId`; or, with `role: "reference"` and a `title`, the original of a new monologue |
| `getJob` | `GET /api/jobs/{id}` | Following a job, once a second |
| `cancelJob` | `POST /api/jobs/{id}/cancel` | Cancel, or discard a failed job's audio |
| `retryJob` | `POST /api/jobs/{id}/retry` | Retry a failed job |
| `getAnalysis` | `GET /api/analyses/{id}` | The full result, including its coaching |
| `requestCoaching` | `POST /api/analyses/{id}/coaching` | Asking the AI model to write the coaching again |
| `listAnalyses` | `GET /api/analyses?limit=20&role=take&monologue=none`, or `…&monologue=<id>` | The General Practice history (takes that belong to no monologue); the takes of one monologue |
| `listMonologues` | `GET /api/monologues` | The monologues, each with its original's ID and a count of its takes |
| `deleteMonologue` | `DELETE /api/monologues/{id}` | Deleting a monologue with its original and its takes |
| `getComparison` | `GET /api/analyses/{id}/comparison/{referenceId}` | A take set against the chosen reference |
| `getWaveform` | `GET /api/analyses/{id}/waveform` | The outline of a sound wave. Only called when the waveform picture is switched on |
| `deleteAnalysis` | `DELETE /api/analyses/{id}` | Delete one analysis |
| `deleteAnalysisAudio` | `DELETE /api/analyses/{id}/audio` | Delete only a kept recording |
| `clearAnalyses` | `DELETE /api/analyses?monologue=none` | Clear the General Practice history. Monologues and their takes are not touched |
| `analysisAudioUrl` | `GET /api/analyses/{id}/audio` | Address of a kept recording, for the player |
| `getFeedback` | `GET /api/analyses/{id}/feedback` | The feedback on the result on view, and the calibration |
| `giveFeedback` | `POST /api/analyses/{id}/feedback` | Saving one piece of feedback, or changing its note |
| `deleteFeedback` | `DELETE /api/feedback/{id}` | Taking one piece of feedback back |
| `getCalibration` | `GET /api/calibration` | The calibration panel when no result is on view |
| `undoCalibration`, `resetCalibration` | `POST /api/calibration/undo`, `…/reset` | The two buttons on the calibration panel |
| `setAdaptive` | `PUT /api/calibration/adaptive` | The "adjust automatically" tick box |
| `correctTranscript` | `POST /api/analyses/{id}/transcript` | Saving corrected words; the answer is the new revision |
| `requestReanalysis` | `POST /api/analyses/{id}/reanalysis` | Analysing a kept recording again; the answer is a job to follow |

- Every failure becomes an `ApiError` carrying the backend's own `code` and `message`, or
  `unreachable` when there was no answer at all. Screens show `message` as it is.
- `types.ts` mirrors the backend's `schemas.py`. When a field changes there, it must change
  here too; nothing checks this automatically.

## 5. Deep dive: the Daily Practice checklist

### 5.1 What it does

Five steps, 15 minutes in total, done on one monologue. One step at a time is the
**current step** and has a countdown. You can start, pause, resume, reset or skip it, tick
any step by hand, and see the last seven days. Since Phase 8 each step has its **tools**
underneath it, so nothing in the routine sends you to another screen (5.12).

| # | Step | Time | Its tools |
| --- | --- | --- | --- |
| 1 | Listen and observe | 3 min | The original recording: a player, and everything measured about it |
| 2 | Mark the delivery | 3 min | The original as a script, with its measured pauses and the words that stood out |
| 3 | Perform the monologue | 4 min | The same script, to perform from |
| 4 | Record and compare | 3 min | The recorder, the comparison of your take with the original, and your takes of this monologue |
| 5 | Correct and repeat | 2 min | The two biggest differences, and the way back to recording |

To change a title, a duration or the number of steps, edit the one object in
`src/features/practice/config.ts`. Nothing else needs changing: the "15-minute" label, the
progress bar and the history all work from that list. Which tools a step gets is decided
by its `id`, in `PracticeChecklist.tsx`.

The checklist, the timer and the history are the same code as before Phase 8 and still
make no request to the backend. What is new is that a round is *on a monologue*, that a
day can hold more than one round, and the tools, which do use the backend.

### 5.2 The files, in the order data flows through them

```
 click a button
       │
       ▼
 components/*.tsx            draw the page, send an "action" such as { type: "start" }
       │
       ▼
 usePracticeChecklist.ts     connects React to the store; runs the ticking clock
       │
       ▼
 practiceStore.ts            holds the current state; saves it; notices a new day
       │            │
       ▼            ▼
 practiceState.ts   storage.ts
 the rules          read / check / write saved data  ──▶  browser localStorage
```

| File | In one sentence |
| --- | --- |
| `config.ts` | The list of steps. |
| `types.ts` | Describes what a day's record looks like. |
| `practiceState.ts` | The rules, as plain functions: given the record and the time now, return the new record. Knows nothing about React, the browser or storage. |
| `storage.ts` | Turns saved text back into records and rejects or repairs anything that looks wrong. |
| `practiceStore.ts` | The coordinator: loads on start, applies actions, saves, moves to a new day, tells the page when to redraw. |
| `usePracticeChecklist.ts` | A React hook. Gives components the current state and starts the clock ticks. |
| `localDate.ts`, `format.ts` | Small helpers for dates and for text like `03:00`. |
| `components/` | What you see. They contain almost no logic. |

The functions inside `practiceState.ts`:

| Function | What it does |
| --- | --- |
| `createDailyRecord` | A fresh day: all steps not started, step 1 current |
| `startTimer`, `pauseTimer`, `resumeTimer`, `resetStep` | The four timer buttons |
| `skipStep` | Marks the current step skipped and moves on |
| `setStepCompleted` | A checkbox being ticked or unticked |
| `selectStep` | "Make current" / "Do this step now" |
| `reconcile` | Finishes a timer whose end time has passed (see 5.4) |
| `remainingMs` | Time left on the current step |
| `summarize` | Completed, skipped, total, percentage, full routine or not |
| `isPristine` | Is this record identical to a brand-new day? (Then it is not worth saving.) |
| `isRoundUntouched`, `isRoundFinished` | Has nothing been done in the round on screen? Has it no step left to do? |
| `setMonologue` | Says which monologue the round is on. Ignored once the round is under way on another (5.10) |
| `switchMonologue` | Abandons the round on screen and starts it again on another monologue |
| `startNextRound` | Files a finished round under "earlier today" and starts another (5.11) |
| `summarizeDay` | A whole day for the history: its rounds, its best round, its monologues |
| `closeOut` | Prepares a record to become history: no live timer |
| `syncWithConfig` | Updates a saved record if the step list in `config.ts` has been edited |

The actions the page can send to the store (`PracticeAction` in `practiceStore.ts`):
`start`, `pause`, `resume`, `reset_step`, `skip_step`, `set_completed`, `select_step`,
`set_monologue`, `switch_monologue`, `start_round`, `reset_today`, `clear_history`,
`dismiss_warning`.

### 5.3 What one day's record looks like

```ts
{
  localDate: "2026-10-11",            // the day, in the device's own timezone
  monologue: { id: "16bb16d4…", title: "The one who knocks" },   // what this round is on
  earlierRounds: [                    // rounds finished earlier today; empty on most days
    { monologue: { id: "16bb16d4…", title: "The one who knocks" },
      completed: 5, skipped: 0, total: 5, finishedAtEpochMs: 1791658400000 },
  ],
  steps: [                            // the round on screen
    { id: "listen", title: "Listen and observe", durationSeconds: 180, status: "completed" },
    { id: "mark",   title: "Mark the delivery",  durationSeconds: 180, status: "skipped" },
    { id: "perform", ...,                                              status: "not_started" },
    ...
  ],
  activeStepId: "perform",            // the current step, or null when none is left
  timer: { status: "running", endsAtEpochMs: 1791658729955 },
  startedAtEpochMs: 1791658549955,
  updatedAtEpochMs: 1791658549955,
  routineCompletedAtEpochMs: null     // set only when all five are completed
}
```

A step is always in exactly one of three states: `not_started`, `completed` or `skipped`.

`monologue` keeps the title as well as the ID, so that the history can still name a
monologue after it has been deleted. Both new fields are missing from a day saved before
Phase 8; such a day loads with no monologue and no earlier rounds, and is otherwise
unchanged.

The timer is in exactly one of three states:

| Timer state | What is stored | Time left is… |
| --- | --- | --- |
| `idle` | nothing | the step's full duration |
| `running` | `endsAtEpochMs`: the clock time at which it will finish | `endsAtEpochMs − now` |
| `paused` | `remainingMs`: how much was left when you paused | `remainingMs` |

### 5.4 How the timer really works

The obvious way to build a countdown is: start at 180, and every second subtract 1. **This
app does not do that**, because browsers do not promise that "every second" really happens.
In a background tab, timers are slowed down or stopped; a refreshed page forgets its counter.

Instead, when you press Start the app stores **the moment the timer should end**
(`now + 3 minutes`). Every 250 ms the page asks "what time is it now?" and shows
`end time − now`. If the tab was asleep for two minutes, the very next check still gives the
right answer, because the end time never moved.

Walkthrough:

1. **Start** at 10:00:00 → saved: `running, endsAt 10:03:00`.
2. **Pause** at 10:01:00 → saved: `paused, remaining 2:00`. Nothing changes while paused,
   however long you wait.
3. **Resume** at 10:30:00 → saved: `running, endsAt 10:32:00`.
4. You **refresh the page** at 10:31:00 → the app reads `endsAt 10:32:00`, sees it is still in
   the future, and shows `01:00`. No new timer is created; it is the same end time.
5. You **close the laptop** and open it at 11:00 → the app reads `endsAt 10:32:00`, sees it
   has passed, marks the step completed once, and moves to the next step without starting it.

Step 5 is called **reconciling**, and it is done by one function, `reconcile()` in
`practiceState.ts`. Every action (start, pause, skip, tick a box…) runs `reconcile()` first.
That one rule is what guarantees a step is completed exactly once and that an old timer can
never complete the wrong step.

Only the current step has a timer. There is one timer in the whole app, kept in one store
that is created once per page load, so it is not possible to end up with two timers running.

The clock is checked:

- every 250 ms while a timer is running (to redraw the countdown);
- every 15 seconds otherwise (only to notice that the date has changed);
- immediately when you come back to the tab or the window.

### 5.5 What each control does

| Control | Effect | Enabled when |
| --- | --- | --- |
| **Start** | Begins the countdown for the current step | There is a current step and the timer is idle |
| **Pause / Resume** | Freezes the time left / continues from it | The timer is running or paused |
| **Reset step** | Stops the timer; the step is back to its full time | The timer is running or paused |
| **Skip step** | Marks the current step *skipped* and moves to the next unfinished step | There is a current step |
| **Checkbox** | Ticks a step complete, or unticks it. Ticking the current step stops its timer | Always |
| **Make current** / **Do this step now** | Switches the current step (un-skips a skipped one). Stops the timer of the step you leave | On steps that are not current and not completed |
| **Show / Hide** a step's tools | Opens or closes what the step is done with. Changes nothing in the checklist | On every step, once a monologue is chosen |
| **Practise again** | Starts another round of the five steps. The finished round stays in today's record | The round has no step left to do |
| **Choose another monologue** | Goes to the Monologues list | Always |
| **Reset today's checklist** | Asks first, then clears today only: every round of it. It stays on its monologue | Today has any progress |
| **Clear history** | Asks first, then deletes previous days only | There is at least one previous day |

When a countdown reaches zero the step is completed and the next unfinished step becomes
current. The next timer does **not** start by itself.

"Next unfinished step" means the next `not_started` step after the current one, wrapping
round to the top of the list. Skipped steps are not revisited automatically.

### 5.6 Days and history

- A "day" is the **local calendar day** on your device. The key is built from the local year,
  month and day, not from UTC. In India, 01:00 on 6 January is still 5 January in UTC, so a
  UTC date would file an early-morning practice under the wrong day.
- A day is saved only once it has some progress. Just opening the page does not create a
  history entry.
- When the date changes, the old day becomes history and a fresh checklist appears.
- If a timer is **running** at midnight it is allowed to finish, and that step counts for the
  day it was started. The fresh checklist appears as soon as that timer stops.
- A timer that was only **paused** when the day changed is dropped; its step stays unfinished.
- The table shows the last 7 calendar days. Older saved days appear under "Older days".
  At most 120 days are kept.
- "Full routine" means all five steps completed. A skipped step never counts as completed.
- A day's row shows the monologue (or monologues) practised, and the figures of the round
  that got furthest: "5 of 5 · best of 2 rounds". One round with every step completed is
  what makes the day a full routine; further rounds are extra.

### 5.7 When saved data is damaged

Saved data is treated as untrusted every time it is loaded, because it can be edited by
hand, cut off, or written by an older version of the app.

| Situation | What the app does |
| --- | --- |
| The saved text is not valid at all | Starts a fresh checklist and shows a message. The unreadable text is left in place until you make real progress, then it is replaced. |
| Some days are invalid | Keeps the valid days, drops the invalid ones, shows a message. |
| A record disagrees with itself (e.g. a timer on a finished step) | Repairs it: the timer is set to idle. |
| The browser blocks `localStorage` | Works in memory only and warns that progress will be lost on refresh. |
| Saving fails (e.g. storage is full) | Keeps working on screen and shows a message. |

### 5.8 Two browser tabs

If the checklist is open in two tabs, each tab is told by the browser when the other one
saves, and reloads the state. Both tabs show the same countdown because both read the same
end time.

### 5.9 Accessibility

- Every control is a real button, checkbox or link, so the whole page works with the
  keyboard, and each has a visible focus outline.
- The current step is marked for screen readers as well as by colour and a "Current step"
  label; completed and skipped steps have text labels, not colour alone.
- The countdown is not announced every second. Instead a hidden line announces changes such
  as "2 of 5 steps completed. Current step: Perform the monologue."
- The page is a single column that fits a phone screen. The four timer buttons sit in a
  two-by-two grid on a phone and in one row on wider screens. Light and dark appearance
  follow the device setting.

### 5.10 The monologue a round is on

The routine is always done on a monologue, and the page learns which from two places:

| Where | What it says |
| --- | --- |
| The address: `/practice?monologue=<id>` | The monologue the user asked for, by pressing "Practise" on it |
| Today's saved record: `record.monologue` | The monologue the round on screen is already on |

They usually agree. When they do not, one rule decides: **a round that is under way stays
on its monologue.**

| Situation | What happens |
| --- | --- |
| Nothing done yet in the round | It follows the address, silently |
| No address, and the record has a monologue | That monologue is shown. This is the "Daily Practice" link in the header on a day already begun |
| No address, no monologue in the record | A list to choose from, the one practised most recently first. The checklist is not shown until one is chosen |
| The round is under way on A, the address asks for B | A notice: "Carry on with this one" (the address is put back to A) or "Switch to the other" (asks first, then clears this round's steps and starts it on B) |
| The round on A is finished, the address asks for B | A notice with "Start a new round on it" |
| The address names a monologue that does not exist | A notice, and the list to choose from |
| The record's monologue has since been deleted | A notice. The timer still works; the tools have nothing to show |

The rule itself is one function, `setMonologue` in `practiceState.ts`, which simply returns
the record unchanged when the round is under way on another monologue. The page calls it
whenever the address or the list of monologues changes, and reads the outcome back from
the record. It never has to work out for itself whether a switch is allowed.

**Choosing a monologue is not progress.** A day is saved only once something has been done
(decision F8), and that is still true: opening a monologue and leaving saves nothing.

### 5.11 Rounds: practising again the same day

One pass through the five steps is a **round**. One round is the day's routine. When the
round on screen has no step left to do, the timer panel shows **Practise again**.

```
 round 1 (on screen)                    after "Practise again"
 ─────────────────────                  ───────────────────────────────────────────
 steps: 5 completed          ──▶        earlierRounds: [ { completed 5, skipped 0, total 5,
                                                          monologue, finishedAt } ]
                                        steps: 5 not started      ← round 2, on screen
```

- A finished round is reduced to a few numbers and kept in `earlierRounds`. The steps on
  screen are always the current round.
- The heading says "Round 2: 1 of 5 steps completed", and a line under the bar says that
  today's routine is already done and this round is extra.
- A round with skipped steps is finished too, and can be followed by another; it is just
  not a full routine.
- The next round can be on another monologue: open that one from Monologues, and the
  notice in 5.10 offers "Start a new round on it".
- A day with a finished round is worth saving even if the next round is never begun.

### 5.12 The tools of each step

`StepList.tsx` draws, under each step, a button "Show …" / "Hide …" and, when open, a box
with that step's tools. The tools themselves are components from `features/monologue/`,
handed to the list by `PracticeChecklist.tsx`:

| Step | Component | What it shows | Where its data comes from |
| --- | --- | --- | --- |
| 1 | `ListenTools.tsx` | The original in the ordinary results view (`<Results mode="reference">`): player, chart, pace, pauses, voice, and the feedback controls for a reference (6.22). An offer to measure it again when the minimum pause has moved | `referenceDetail` in the store |
| 2, 3 | `ScriptView.tsx` | The script of the original (5.13) | The same |
| 4 | `RecordTools.tsx` | Record or upload, language, keep; "Analyse and compare"; the progress of the job; then the take's headline figures, the comparison with the original (6.15), a link to the take's full analysis; and the list of your takes of this monologue | `viewed`, `comparison` and `takes` in the store |
| 5 | `CorrectTools.tsx` | The two largest differences from the comparison, each with **Original** and **Yours** to play; "Record another take", which opens step 4 and scrolls to it | `comparison` in the store |

**When tools are open.** Nothing about this is saved; it is worked out each time the page
is drawn:

```
 open  =  what the user last chose for this step, if they pressed Show or Hide
          otherwise:  it is the current step,  or  something of its own is going on
```

"Something of its own is going on" matters for step 4. Its timer is three minutes, and an
analysis with AI coaching can take longer than what is left of it. When the timer runs
out, the checklist moves on to step 5, as it always did. Step 4's tools stay open all the
same, because a recording is being made, a take is being analysed, or a take is on view.
A step's tools can also be opened at any time, whether or not it is the current step and
whether or not its timer is running: the timer is a guide, not a lock.

**Which take is "on view".** The take that was just analysed, or one opened with
**Compare** in the list of takes. The page only ever treats a take as on view if it was
recorded for the monologue being practised: the store is shared with the other screens
(decision F36), so it may be holding something from one of them.

**Feedback on this page** is about the original recording, in step 1. Feedback on a take
is given on the take's own page (6.14), where its coaching is.

### 5.13 The script of the original

`ScriptView.tsx`, with its logic in `features/monologue/script.ts`.

```
 1. I am not in danger, Skyler.                         159 WPM   Play
 ‖ pause 1.6 s   at 0:02.3
 2. I am the danger.                                    198 WPM   Play
 ‖ pause 1.1 s   at 0:05.1
 3. A guy opens his door and gets shot, and you think that of me?     217 WPM   Play
                                               ‾‾‾ ‾‾‾‾‾
 ‖ pause 2.3 s   at 0:10.0
 4. No, I am the one who knocks.                        206 WPM   Play
```

| What is shown | Where it comes from |
| --- | --- |
| One line per phrase | The original's segments, in order |
| The words | The recognised words of that phrase; a phrase with no timed words falls back to its own text |
| `‖ pause 1.6 s` after a line | The measured pause that follows that phrase. A long silence (5 s or more) is marked `‖‖` |
| An underlined word | An emphasis candidate: a word that measured louder or higher than the speaker's typical word. A screen reader hears "(louder)" or "(higher)" after it |
| ▲ faster / ▼ slower | The phrase's pace against the speaker's own typical pace |
| **Play** | Plays that phrase of the original, when its recording is available |

`buildScript` only rearranges a stored result. It measures nothing and infers nothing: a
pause is there because the analysis found one, a word is marked because it is in the
list of emphasis candidates. A marked word is matched to its candidate by phrase and
start time, not by its text, so that the same word said twice is marked only where it
stood out. The legend under the script says what is not detected (emphasis made by slowing
down) and where to correct a misheard word (step 1).

## 6. Deep dive: General Practice

### 6.1 What it does

General Practice is for any speaking you want measured that has no original recording to
set it against: a talk, a reading, a test of how you sound today. A take of a monologue
is recorded in Daily Practice instead (5.12), and is not listed here.

You pick a delivery profile, record yourself or choose an audio file, and press **Analyse
recording**. The page then follows the analysis job, shows the results with coaching on what
to change for the next take, and keeps a history you can reopen, compare against, and delete.
Beside each pause, phrase and correction you can say where the analysis got it wrong, and
at the bottom of the page a panel shows what that feedback has changed (6.18 to 6.20).

The measuring and the coaching both happen in the backend (see the science document). This
screen's job is everything around them: getting the audio, following the job honestly,
showing the numbers with their caveats, and making it plain who wrote the coaching and what
it rests on.

### 6.2 The files, in the order data flows through them

```
 components/*.tsx          draw the page; call actions such as store.submit(...)
        │
        ▼

        │
        ├──▶ generalStore.ts    the run in progress, the result on view, the history
        │         │
        │         ▼
        │      api.ts  ──▶  the backend (HTTP)
        │         ▲
        ├──▶ feedbackStore.ts   the feedback on the result on view, and the calibration
        │
        ├──▶ recorder.ts        microphone recording  ──▶  the browser's MediaRecorder
        │
        └──▶ healthMonitor.ts   is the API / worker / speech model / AI model there?
```

| File | In one sentence |
| --- | --- |
| `types.ts` | The TypeScript shapes of the backend's JSON. |
| `api.ts` | One function per backend request; turns every failure into an `ApiError`. |
| `generalStore.ts` | Holds the screen's state and every action that changes it. No React. |
| `recorder.ts` | Start, stop and discard a microphone recording; reports problems in plain words. No React. |
| `healthMonitor.ts` | Asks the backend how it is every 10 seconds, only while the screen is open. |
| `validation.ts` | Is this file an audio type, non-empty and under the size limit? |
| `compare.ts` | The difference between two attempts, metric by metric. |
| `coaching.ts` | What to play for a piece of evidence, which phrase a correction is practised on, what to do when the AI model is unavailable, and whether asking again could help. |
| `voiceRange.ts` | The words for each range and marker, where the mark goes on a scale bar, and which phrases left the range aimed for. Works no measurement out. |
| `feedbackStore.ts` | Holds the feedback on the result on view and the calibration; one request per action. No React. |
| `feedback.ts` | Which feedback belongs to which pause or phrase, the silences inside a phrase, whether labels have changed, how the minimum pause is worded. |
| `timeline.ts` | Scales, axis ticks and "what is happening at this moment" for the chart. |
| `audioDuration.ts` | Works out the length of a browser-made recording so it can be seeked. |
| `format.ts` | Text for times, numbers, changes, profile names, stage names. |
| `useGeneralPractice.ts` | Creates one of each store for the page and exposes them as hooks, plus the segment player. |

This section describes the machinery as General Practice uses it. The monologue screens
use the same store, the same recorder, the same run panel and the same results view; what
they add is in 5.12, 5.13 and 6.14.

Like the checklist, the logic lives in plain files that receive what they need from outside
(the backend client, the timer, the microphone). That is what lets the tests script a
backend, a microphone and the passage of time without a browser.

### 6.3 The life of one analysis on screen

`generalStore.ts` keeps one **run** at a time. It is always in exactly one phase:

```
            submit()
   idle ───────────────▶ submitting ──────▶ tracking ──────▶ loading_result ──▶ done
    ▲                        │                │   ▲
    │                        │ refused, or    │   │ retry()
    │ dismissRun()           │ no answer      ▼   │
    └──────────────────── failed ◀────── job failed
                             ▲
                             │
          cancelled ◀── job cancelled
```

| Phase | What the screen shows | What is happening |
| --- | --- | --- |
| `idle` | Nothing | No analysis in progress |
| `submitting` | "Sending the recording…" | The upload request is in flight |
| `tracking` | Queue position or the five stages, and Cancel | The job is `queued` or `running`; its status is fetched once a second |
| `loading_result` | "Loading the result" | The job succeeded; the full result is being fetched |
| `done` | "Analysis finished", and the results | The result is on screen and in the history |
| `cancelled` | "Analysis cancelled" | The worker has really stopped |
| `failed` | The reason, and Retry / Discard / Send again / Dismiss as appropriate | See 6.5 |

Rules the store enforces:

- **One at a time.** `submit()` does nothing while a run is `submitting`, `tracking` or
  `loading_result`, so a double click cannot start two analyses. The Analyse button is also
  switched off, and the backend has its own guard (the idempotency key).
- **Stages, not percentages.** The backend reports which of five stages it is in; the last,
  "Writing the coaching", is the AI model at work. The screen lists them with done / in
  progress / waiting. It never invents a percentage.
- **A cancelled job is not called cancelled early.** After pressing Cancel on a running job
  the screen says "Cancelling" and keeps checking until the backend reports `cancelled`.
- **Old answers are ignored.** Each run has a number. If you dismiss a run and start another,
  a late answer belonging to the first one changes nothing.

**A second kind of run.** Pressing "Write the coaching again" (see 6.9a) starts a run that
goes through the same phases with one difference at the start: instead of uploading audio,
it asks the backend for a coaching job. The store remembers which kind the run is in two
extra fields, `runKind` (`"analysis"` or `"coaching"`) and `coachingFor` (the analysis the
coaching belongs to). The run panel uses them to choose its words and to show one stage
instead of five. Because it is the same run, the same rules apply: one at a time, followed
once a second, survives a refresh, can be cancelled.

### 6.4 Following a job

- The status is fetched **once a second** (`POLL_MS`), using a single timer that is re-armed
  after each answer. There is never more than one check in flight.
- If the backend stops answering, the last known status stays on screen with "Lost contact
  with the local backend. Still trying", and the checks slow down: 2 s, 4 s, then every 5 s
  (`MAX_POLL_MS`). When it answers again, checks go back to once a second.
- If the job's status says `workerAlive: false`, the screen says the worker is not running
  and shows the command to start it.
- **Refreshing the page does not lose the job.** While a job is in progress its ID is kept in
  `localStorage`. When the page loads, it looks for that ID and carries on following the job.
  What is lost on refresh is only the in-memory copy of the audio (see 6.8).

### 6.5 When something goes wrong

| What happened | What the screen offers | Why |
| --- | --- | --- |
| The backend refused the file (wrong type, too big, not really audio) | The backend's message; Dismiss | Sending the same file again would be refused again |
| The upload got no answer at all | **Send again** | The same recording is sent with the *same* idempotency key, so if the first attempt did arrive, no second job is created |
| The job failed, and the backend says a retry can work | **Retry**, **Discard** | The backend is still holding the audio; Retry needs no new upload. Discard deletes it |
| The job failed for good | The reason; Dismiss | Record or upload again |
| The job no longer exists | A message; Dismiss | For example, history was cleared in another tab |
| The AI model could not write the coaching *during an analysis* | Nothing to do: the analysis succeeds, and the Coaching section says it was written from fixed rules and why | Coaching is optional; the measurements must not be lost to it |
| "Write the coaching again" failed | The reason, what to do about it (for example the command to start Ollama), **Try again**, Dismiss. Shown both in the run panel and beside the button | The earlier coaching is untouched, so nothing was lost |

### 6.6 Recording

`recorder.ts` wraps the browser's `MediaRecorder`. Its states:

```
 idle ──start──▶ requesting ──permission given──▶ recording ──stop──▶ recorded
   ▲                 │                               │                    │
   │                 └── refused / no microphone ────┴──▶ error           │
   └──────────────────────────── discard ─────────────────────────────────┘
```

- **Format.** The browser chooses: WebM (Opus) in Chrome and Firefox, MP4 in Safari. The
  file is sent to the backend as it is.
- **Elapsed time** comes from the clock, like the checklist timer, not from counting ticks.
- **The length limit** comes from the backend (10 minutes by default). Recording stops by
  itself at the limit and says so.
- **The microphone is always released** — on stop, on discard, on any error, and even if
  permission arrives after you have already pressed Cancel. The browser's recording
  indicator should never stay on by accident.
- **No audio is never reported as success.** If nothing was captured, the state is an error
  ("No audio was captured"), not a zero-length recording.

| Problem | Message shown |
| --- | --- |
| Permission refused | Microphone access was blocked. Allow the microphone for this site… |
| No microphone | No microphone was found. Connect one, or upload a file instead. |
| Microphone in use or failed to start | The microphone could not be started. Another app may be using it… |
| Browser cannot record | This browser cannot record audio here. You can upload a file instead. |
| Page is not secure | Recording only works on a secure page. Open the app at http://localhost… |
| Nothing captured | No audio was captured. Check that the microphone is working… |

### 6.7 Uploading

The file picker accepts the types the backend lists. Before anything is sent, `validation.ts`
checks three things and explains a failure in a sentence: is it an audio type, is it empty,
is it over the size limit. The backend makes the same checks again, and also opens the file
to confirm it really is audio, which the browser cannot do cheaply.

### 6.8 Playing the recording back

- A recording you just made or chose is held in the page's memory and attached to its
  result, so the results can be listened to. A **kept** recording is loaded from the backend
  instead. If neither exists, the Play buttons are switched off and a note says why.
- **Play** on a segment plays just that phrase. Play on a pause plays the pause with 1.5 s
  either side. Clicking the chart plays from that moment.
- Stopping at the end of a segment is checked on every animation frame (about 60 times a
  second), with the audio element's own time events as a fallback when the tab is in the
  background.
- **A fix for browser-made recordings.** A recording made by `MediaRecorder` carries no
  length, so the audio element reports a duration of *Infinity* and cannot jump to a
  position: "Play segment" would do nothing. `audioDuration.ts` asks the element to jump far
  past the end, which forces the browser to work the length out, then puts playback back at
  the start. After that, jumping works normally.

### 6.9 The results screen

From top to bottom, in `Results.tsx`:

| Section | What is in it |
| --- | --- |
| Header | Date, profile, language (and how it was known), length. Which revision this is, with links to the other results from the same recording (6.20). Close and Delete |
| Warnings | Anything that affects how far the numbers can be trusted |
| Older settings | Only when the minimum pause has moved since this result was made: says so, and offers to analyse the recording again (6.20) |
| Summary | **Speech-active WPM** as the one large figure; then whole-clip WPM (labelled "including pauses"), words, time speaking, pauses, median and longest pause |
| Recording | The player, and the timeline chart |
| Coaching | Who wrote it; a four-line delivery summary; up to three corrections, each with **Useful / Not useful**; what is already working; targets for the next take; what is uncertain or not measured; a button to have it written again. See 6.9a |
| Pace | Your typical pace, pace variation, slowest and fastest segment; phrases well away from your typical pace; the segments table, each row with **Report a problem** (6.18) |
| Pauses | Average, total, pause share, silence before/after; the pauses table, each row with a **Your feedback** list (6.18) |
| Voice | Loudness and pitch variation, pitch range, median pitch, voice above background, hesitation sounds, breaths (unavailable); emphasis candidates |
| Where your voice sits | Pitch and resonance, each placed in a lower, neutral or higher range, for the recording and for every phrase. See 6.9b |
| Your feedback on this result | Everything said about this result, with what each piece does (6.18) |
| Compare | This attempt against an earlier one |
| Details | The transcript, and the settings that produced the numbers |

How the caveats are shown:

- A value that could not be measured shows **—**, never 0, with the reason underneath.
- A value that is an estimate carries an **Estimate** label.
- Each headline number has one line under it saying what it is. The formulas for the two
  WPMs are always visible, not hidden in a tooltip.
- Measurements the chosen profile depends on most carry a **Profile focus** tag. Whether
  they suit the profile is said in the Coaching section.
- Wherever the screen says how long a silence must be to count as a pause, it reads the
  value from the result itself (`settings.min_pause_ms`): "half a second" for a result made
  at the default, "0.4 seconds" for one made after the minimum pause was lowered.

### 6.9a The Coaching section

Drawn by `Coaching.tsx` from the `coaching` object in the result. It sits directly under the
recording and its chart, above the detailed tables, because it is the answer to "what do I
do next", and its play buttons use the player just above it.

| Part | Where the words come from |
| --- | --- |
| "Worded by the AI model llama3.1:8b…" or "Written from fixed rules, not by the AI model" | `coaching.source`, `coaching.model`, `coaching.notice` |
| Delivery summary: Pace, Pauses, Voice, Clarity | `coaching.summary`. Written by the backend's code |
| Each correction's title, **Why it matters** and **Drill** | The AI model, or a template |
| Each correction's **Measured** line | The finding it points at. Written by the backend's code |
| Each correction's **Practise on** line | The phrase's own words from the transcript, looked up by this screen. Never the model's wording |
| What is already working | A note (AI model or template) and the finding it rests on |
| Targets for the next take | `coaching.nextTake`. Always written by template |
| Uncertain or not measured | `coaching.caveats`. Always written by the backend's code |

So in every correction the reader can see three different things side by side: what was
measured, what the coach makes of it, and the exact stretch of audio to listen to. **Play**
beside a phrase plays that phrase; beside a pause it plays the pause with a second and a
half either side.

How the three sources look:

| `source` | What is shown |
| --- | --- |
| `ai` | One muted line: which model, that it runs on this computer, that it was given the transcript and measurements and never the audio, when, and how long it took. If some of its suggestions were removed by the checks, a warning says how many |
| `rules` | A notice: "Written from fixed rules, not by the AI model", the reason, and what to do about it, with the command where there is one (`ollama serve`, `ollama pull llama3.1:8b`). The corrections are still shown in full |
| `none` | Only the reason (no speech, or too short), the summary and the caveats |
| no coaching stored | "No coaching is stored for this analysis", and the button |

**Writing it again.** The button at the bottom ("Write the coaching again", or "Ask the AI
model for coaching" when the current coaching is not from the model) calls
`store.regenerateCoaching(analysisId)`. It is:

- switched off while any run is in progress, and when the health check says the AI model is
  not available, each time saying why in the line beside it;
- not shown at all when asking again could not change anything: there was nothing to coach
  on, or nothing measured needs correcting;
- followed in two places at once: the run panel near the top of the page, and one line
  beside the button itself, because the panel may be scrolled out of view.

When the new coaching arrives it replaces the old on screen. If you opened a different
analysis while waiting, you are left where you are; the new coaching is there when you go
back.

**Rating a correction.** Under each correction are two toggle buttons, **Useful** and **Not
useful**. Pressing one saves it; pressing the same one again takes it back. The sentence
the backend sends back is shown underneath ("Counts towards lowering the priority of
corrections about overall pace. 1 of the 3 reports needed…"). A rating is matched to its
correction by what the correction is about as well as by its ID, so it cannot end up on a
different correction after the coaching has been written again.

**When your pause labels have changed.** If you have marked a pause intentional or
accidental since the coaching was written, a notice says the coaching does not take that
in yet, and the button becomes "Write the coaching again with my labels". In this one case
the button works even when the AI model is not available: coaching from the fixed rules
that knows about the labels is already an improvement, and the line beside the button says
that is what will happen.

### 6.9b Where your voice sits, and the voice goal

Added in Phase 9. How pitch and resonance are measured, what the three ranges are and
what the percentage means is in the science document, sections 9a and 9b. This section is
about how they are shown.

**The goal, on the recording form.** Under "Language spoken", in General Practice and in
step 4 of Daily Practice, there is one more list box, **Voice goal (optional)**:

| Choice | The line under it |
| --- | --- |
| No goal | The general note only |
| Keep my voice lower | "Coaching will point at the phrases where your pitch or resonance left the lower range." and the general note |
| Keep my voice higher | The same, for the higher range |

The general note says that the voice is measured whether or not a goal is chosen, that
without one nothing about it is judged, and that the ranges describe how a voice is
typically heard and not who is speaking. The choices and both texts come from the backend

original does not show the list: a reference has no goal.

The choice is **remembered in the browser** (section 7), because someone working on their
voice wants the same goal every day and should not have to set it for each take. It is
sent with the recording, and the result keeps the goal it was made with. Changing the

| Part | What it shows | Notes |
| --- | --- | --- |
| The goal line | One sentence counted from the phrases: how many stayed in the range | Only with a goal. Counts only the phrases that could be placed |
| Two cards | The value in Hz, the range with its edges, the position in words, and a bar | A value that could not be measured shows the reason in place of a number, never 0. An estimate carries the **Estimate** label and says why |
| The bar | The three ranges drawn in proportion to their width, with a mark at the value | Decoration for sighted users: everything it says is also in the words above it, so it is hidden from screen readers |
| Together | The one-word marker and how such a voice is typically heard | For "mixed": "Pitch and resonance point different ways, so a listener is given two different cues." |
| Phrase by phrase | A table: each phrase's pitch, resonance and marker, and a Play button | A phrase that left the goal's range is marked **Outside your goal** in words, not only by colour |
| The ranges (closed by default) | The table of all three ranges for both scales, as stored with this result; what the percentage means; the limits | Read from the result, so an old result always shows the ranges that placed it |

The position is worded differently for the neutral range ("60% of the way to its
middle"), because there the percentage counts from the edges inwards.

A result stored before Phase 9 has no voice range. The section then says so, and that
analysing the recording again adds it if the recording was kept. A recording with no
speech says there is no voice to place.

**In the coaching.** With a goal, the two voice findings can appear as corrections ("Keep
your pitch in the lower range", "Deepen your resonance") or under "What is already
working", like any other finding, with **Measured** beside them and a Play button for the
phrase furthest from the range. That needed no new component: the Coaching section draws
whatever findings the backend sends (6.9a).

### 6.10 The timeline chart

`TimelineChart.tsx` draws two panels on one shared time axis, as plain SVG:

- **Top: loudness over time**, a line with a light wash under it. The scale is fitted to the
  recording's own loudest moment and reaches 50 dB below it.
- **Bottom: where you were speaking**, as bars. The gaps are pauses. Medium and long pauses
  are labelled with their length when the label fits; when it does not, it is left out
  rather than squeezed. ▲ and ▼ mark phrases faster or slower than your typical pace.

How it was built to be readable and usable:

- **One colour**, because there is one thing being shown: your voice. The light and dark
  values were each chosen for their own background and checked with a palette validator
  for contrast.
- **Two panels, not two scales on one panel.** Loudness and speech are different kinds of
  measurement; overlaying them on one plot with two y-axes would suggest a relationship that
  is only an artefact of how the axes were lined up.
- **Hover** anywhere on the chart for a readout of that moment: the time, the loudness, and
  whether it falls in a segment (with its WPM) or a pause (with its length). The pointer only
  has to be near a moment, not on the line.
- **Keyboard:** the chart can be focused; the left and right arrow keys move through it
  (Shift moves faster, Home and End jump), and Enter plays from that moment. A screen reader
  hears the same readout.
- **Nothing is only in the chart.** Every value is also in the tables below it.
- It is drawn at the real pixel width of its container, so text stays the same size on a
  phone, and the number of axis labels adapts.

### 6.11 Comparing with an earlier attempt

`compare.ts` lines up nine headline metrics of this attempt and an earlier one. The earlier
attempt defaults to the one just before, and any earlier one can be chosen. In General
Practice the earlier attempts are the other analyses in its history; on a take's own page
they are the other takes of the same monologue.

- Only the **change** is shown: "+16.5 WPM", "−0.48 s". Never "better" or "worse". Whether a
  slower pace or a longer pause is an improvement depends on what you were going for.
- If either side could not be measured, the change is — rather than a made-up number.
- The change is calculated from the rounded values that are shown, so the three columns
  always add up.
- Loudness figures are compared too, but remember they are relative to each recording.
- If the two attempts were analysed with a different minimum pause, a warning says so, with
  both values: their pause counts and phrase speeds are then not like for like.

### 6.12 History

The list comes from the backend (`GET /api/analyses?monologue=none`), newest first, 20 at
a time. It holds the analyses made in General Practice: the takes that belong to no
monologue. Each row has View, Delete, and — if the recording was kept — "Delete recording",
which removes only the audio. "Clear all history" deletes every analysis in this list and
its kept recording. All three ask for confirmation, and none of them touches the Daily
Practice checklist, a monologue, or a take recorded for one.

A later result made from the same recording is its own row, marked "Revision 2: transcript
corrected" or "Revision 3: analysed again" (6.20). Deleting an analysis also deletes the
feedback given on it.

### 6.13 When the backend is not ready

`healthMonitor.ts` checks `GET /api/health` when the screen opens and every 10 seconds while
it stays open. The screen shows the first problem it finds, with the exact command to fix it:

| Problem | Notice |
| --- | --- |
| No answer | The local backend is not running… |
| Database not usable | The backend cannot use its database… |
| Worker not running | The analysis worker is not running. You can submit a recording, but it will wait… |
| Speech model missing | The speech model is not downloaded, so analyses will fail… |
| AI model not available (Ollama not running, model not installed, or its address not on this computer) | AI coaching is not available… Recordings are still measured in full, and the coaching is written from fixed rules instead… with the command to fix it |

The last one is the only notice that does not stand in the way of anything: it is an
ordinary notice, not a warning, and it is not shown at all if AI coaching was switched off
on purpose (`AI_COACHING=off`).

### 6.14 Monologues, their takes, and a take's own page

A **monologue** is one piece you practise. To the backend it is a reference recording (the
original performance) together with the takes recorded for it. On screen the reference is
called "the original".

Three screens are built on it:

| Where | What it is for |
| --- | --- |
| `/monologue` | The list. Add a monologue, open one to practise, delete one |
| `/practice?monologue=<id>` | Daily Practice on it (section 5) |
| `/monologue/take?analysis=<id>` | The full analysis of one of its takes |

All of them, and General Practice, use **the same store**. `useGeneralPractice.ts` creates
one for the whole app, so a job started on one screen is followed on the others, and there
is one place where "only one run at a time" is enforced.

**What the store holds for monologues** (`generalStore.ts`):

| State | Meaning |
| --- | --- |
| `monologues` | The list, from `GET /api/monologues`. Each item has `monologueId`, `referenceId` (its original, in the newest revision), `title`, `takeCount`, `lastTakeAt` |
| `monologueId` | The monologue the screen on view is about. `null` on a screen that is about none |
| `takes` | That monologue's takes, newest first, from `GET /api/analyses?monologue=<id>` |
| `selectedReferenceId` | The reference on view: the watched monologue's newest, unless an earlier revision was opened |
| `referenceDetail` | That reference's own full result, for studying it and for the script |
| `comparison` | The take on view against that reference: `none`, `loading`, `ready` or `error` |
| `history` | The General Practice history: takes that belong to no monologue |
| `waveforms` | Sound-wave outlines by analysis ID. Empty until one is asked for |
| `runRole` | Whether the run in progress is for a take or a reference |

| Action | What it does |
| --- | --- |
| `watchMonologue(id)` | Says which monologue the screen is about. Loads its takes and chooses its original. `null` lets go of both |
| `submit({ …, monologueId })` | Sends a take of that monologue. It is the ordinary `submit`, followed, cancelled and recovered like any analysis |
| `submit({ …, role: "reference", title })` | Adds a monologue |
| `selectReference(id)` | Opens another revision of the original |
| `deleteMonologue(id)` | Deletes a monologue, its original and its takes, after a confirmation that says how many takes go with it |
| `loadWaveform(id)` | Fetches one outline, once |

**A screen says which monologue it is about; the store does the rest.** Daily Practice
calls `watchMonologue` with the monologue of the round. The take page calls it with the
monologue its take belongs to. From then on the store keeps three things in step without
being asked: the takes of that monologue, its original for study, and the comparison.

**The comparison keeps itself up to date.** No component asks for it. Whenever the take
on view, the watched monologue or the chosen reference changes, one function,
`syncWithSelection`, works out which pair is now wanted and fetches that comparison,
unless it already has it. A slow answer for a pair that is no longer wanted is thrown
away. Two rules are built into it:

- a take is compared only if it was recorded for the monologue being watched;
- a take that belongs to no monologue is compared with nothing.

**The original follows its monologue.** When a monologue is first watched, its newest
reference is chosen. It is chosen again only when that reference itself changes: its words
were corrected, or it was measured again. In between, an earlier revision the user has
opened (from the links in the header of step 1) stays open; refreshing the list does not
take it away.

**The Monologues page** (`MonologueList.tsx`), top to bottom:

1. **Your monologues.** One row each, the one practised most recently first: its name,
   length, language and when it was added; how many takes it has and when the last was;
   **Practise**, a link to `/practice?monologue=<id>`; and **Delete**, which asks first
   and names the number of takes that will go with it.
2. **Add a monologue** (`AddMonologue.tsx`): a name, the original recording as a file, the
   language, and "Keep this recording", ticked by default (decision F39). Open from the
   start when there is no monologue yet.
3. **The run panel**, while the original is being measured: four stages, then "Monologue
   added".

**A take's own page** (`TakeAnalysis.tsx`). The link "Full analysis" beside a take, in
step 4 of Daily Practice, leads here.

- It is the ordinary results view (6.9): summary, recording, coaching, pace, pauses,
  voice, feedback, and "compare with an earlier attempt", where the earlier attempts are
  the other takes of the same monologue.
- Between the coaching and the pace tables sits **Against the original**: the comparison
  of this take with its monologue's original (6.15).
- The feedback controls (6.18) are here, and the calibration panel (6.19) is at the
  bottom.
- "← Back to practising …" at the top, and **Close results**, go back to Daily Practice
  for that monologue. Deleting the take does the same.
- The address is read when the page opens and when it changes. After that the page shows
  whatever the store has on view, so a new revision of the take (a corrected transcript,
  a fresh analysis) takes its place without a second request.
- Opened with the ID of something that is not a take of a monologue, it says what that
  thing is and where it is shown.

**What General Practice no longer has.** Until Phase 8 its results carried a section
"Compare with a reference recording", with a menu of references. That section is gone
(decision G14 in the main document). If a take recorded for a monologue is on view in the
shared store when General Practice is opened, it is not shown there; a notice links to
its own page.

### 6.15 The comparison section

Drawn by `ReferenceComparison.tsx` from the `comparison` in the store. The comparing itself
is done by the backend (science document, section 14); this component only shows it. It
appears in two places: under step 4 of Daily Practice, for the take on view, and on a
take's own page. The tables say "reference" for the original, which is the word the
measurements use.

| Part | What it shows |
| --- | --- |
| Two players | "Reference: <its name>" and "Your take". Each has its own player, so one can be heard straight after the other |
| The note | How well the two could be lined up: "97% of the reference's words were found in your take…". A warning when they could not be |
| Biggest differences | Up to five sentences written by the backend, each with **Reference** and **Yours** to hear that spot in both |
| Pause by pause | After which words; the reference's pause; yours; the difference; listen to both. "No pause" where one has none, "Not found in your take" where the spot could not be located |
| Phrase by phrase | Each phrase of the reference; its pace in both; the difference in WPM and as a percentage. A phrase too short or too poorly matched is listed without a pace, and says why |
| The recordings as wholes | Fourteen figures: yours, the reference's, the difference |
| What this comparison does not tell you | Folded away: what is not compared (loudness, how high the voice is), and any warnings about either recording |
| Show waveform comparison (visual only) | A checkbox, off by default. See 6.16 |

A **Reference** or **Yours** button is switched off when that recording is not available to
play: it was not kept and is not in this page's memory.

The wording is always "difference". The line under the list says so: "Differences, not
mistakes. Whether to follow the reference at each point is your decision."

### 6.16 The waveform picture

`WaveformComparison.tsx`, with its arithmetic in `waveform.ts`. It is switched on by the
checkbox "Show waveform comparison (visual only)", which is **off every time** the section
is opened.

- **Nothing is fetched until it is switched on.** Ticking the box calls `loadWaveform` for
  the two recordings; that is the first moment the outlines are requested. Confirmed in the
  browser: no waveform request before ticking, two after.
- **Switching it on or off changes nothing else.** It fetches a picture and draws it. It
  submits nothing, starts no job, and no figure on the page is taken from it. A store test
  checks that the analysis on view, the run and the comparison are the very same objects
  before and after.

What is drawn (a hand-made SVG, like the timeline chart):

- One lane per recording on a shared time axis in seconds, each named above its lane: the
  reference in orange, your take in blue. The legend's checkboxes hide either one.
- **Each keeps its real length.** The axis is as long as the longer of the two; the shorter
  simply ends earlier. Neither is stretched.
- **One above the other** by default, or **Overlaid** in one lane, half see-through.
- **Shift your take by … seconds.** A number you type. The two are never lined up for you.
  The sentence above the chart always says what the shift is ("Your take is shifted 6.5 s
  later"), and it changes only the picture.
- **Height is relative waveform amplitude.** By default both are drawn on the same scale,
  where full height is the loudest a recording can be. "Stretch each waveform to its own
  loudest point" is off by default, and when on says that it hides any real difference in
  level.
- Moving over the picture shows where that moment falls in each recording.
- Above the chart, in words: each recording's length and the shift. The picture is never
  the only way to learn them.

When something is missing, it says which and why:

| Situation | What is shown |
| --- | --- |
| Only one recording exists | Its waveform alone, and that a second is needed to compare |
| A recording was analysed before Phase 5 | "No waveform is stored for … Analysing it again will store one" |
| The outline could not be loaded | The reason, for that recording only |

The outline arrives with at most 2,000 points per recording. `outlineColumns` merges them
down to one lowest/highest pair per pixel column, so the drawing is two shapes however long
the recording is.

### 6.17 Accessibility

- Every control is a real button, input or link with a visible focus outline.
- Profiles are radio buttons in a group; the record/upload switch is a pair of toggle buttons.
- Status changes in the run panel are announced politely to screen readers; errors are
  announced as alerts.
- Tables have captions and header cells. Play buttons say what they play ("Play segment 3").
- Every table in the comparison has a caption and header cells. The listen buttons say
  what they play ("Play the reference around “…I am the danger”"). The waveform has a
  written summary of both lengths and the shift, and its lanes are named in words as well
  as by colour. The two colours were checked for colour-blind separation in light and dark.
- The corrections are a numbered list, and each one's parts (Measured, Why it matters,
  Drill, Practise on) are a labelled list, so a screen reader announces which is which. The
  progress line beside "Write the coaching again" is announced when it changes.
- Trust is never shown by colour alone: "Estimate" and "Unavailable" are written out.
- Tables scroll sideways inside their own box on a phone; the page itself never does.

### 6.18 Feedback on a result

Feedback is optional. A result is complete without it, and nothing on the page waits for
it. This section describes it on one of your own takes: in General Practice, or on the
page of a take of a monologue (6.14), which shows the same results view. A monologue's
original takes a smaller set of the same controls, in step 1 of Daily Practice (6.22).

There is no separate "feedback form". Each control sits next to the thing it is about, so
that "which pause?" never has to be asked:

| Where | Control | What can be said |
| --- | --- | --- |
| Each row of the **pauses** table | A list, "Your feedback" | Intentional · Accidental: I lost my place · Not a pause: I was still speaking · Too short to split the phrase here · No feedback |
| Each row of the **segments** table | "Report a problem", which opens a form under the table | A pause was missed in this phrase · Its WPM looks too high · Its WPM looks too low · The words are wrong |
| Each **correction** in the coaching | Two toggle buttons | Useful · Not useful |
| The **"Your feedback on this result"** section | Two buttons | The overall WPM looks too high · too low |

Choosing from the pause list saves at once; choosing "No feedback" takes it back. The
sentence the backend returns is shown under the control: what the feedback does, in plain
words. The screen never works that sentence out for itself.

**Reporting a missed pause.** The form asks *where*, and offers real candidates first:

```
 Where was the pause?
 Listed first are the silences the detector heard inside this phrase that were too short
 to count as pauses.
   ( ) At 0:04.3: a silence of 0.36 s, after "am"         Play
   (•) After a word I pick
         [you] [all] [know] [exactly] [who] [I] [am] ‖ pause here [so] [say] [my] name
         Between "am" and "so", at about 0:04.4. The nearest silence the detector
         heard is 0.36 s long, at 0:04.3.                  Play
   ( ) Where the player is now: 0:03.4
   ( ) I cannot say exactly where
```

Each candidate can be played with a second either side. "Where the player is now" is
available when the recording is playing or paused at a point inside the phrase. These are
the four ways of pointing at a moment: a silence the app measured, a word, the playhead,
or not at all, in which case the report is saved and the backend says it cannot count.

**Picking a word** (Phase 7) is for when you know *where in the sentence* you paused and
not at what time, and it is the only precise way when the recording was not kept and
cannot be played. Each word of the phrase is a button, except the last: a pause after the
last word is the end of the phrase, which is a pause already. Pressing a word means "the
pause came after this one". The screen then says what it will send and what the detector
heard there:

| Step | Where | What happens |
| --- | --- | --- |
| The gaps | `wordGaps` in `feedback.ts` | For each pair of neighbouring words, the moment halfway between the end of one and the start of the next, kept inside the phrase |
| The preview | `silenceNear` in `feedback.ts` | The silence nearest that moment, if one lies within half a second. This is the backend's own rule, copied only to show its answer in advance |
| Saving | `store.give` | The ordinary missed-pause report with `atSeconds` set to that moment. The backend needed no change |

Until a word is pressed, "Save this report" is off and says "Pick a word above first."
Words are shown without the punctuation the speech recogniser attaches to them ("Skyler."
is shown as "Skyler"), here and wherever a word is named.

**Saying the words are wrong.** The form shows the phrase's words in a box to edit. "Save
corrected words" sends them (6.20). "Only flag it, without correcting" saves a note that
the transcript is wrong and changes nothing.

**Saying the WPM looks wrong.** Nothing changes. The saved entry shows a review: the
arithmetic ("16 words ÷ 4.51 s of speaking × 60 = 212.9 WPM") and, under labelled headings,
what was measured for the words, the speaking time and the word timing, each saying which
feedback would correct it. The review is built by the backend and only displayed here.

**The section "Your feedback on this result"** gathers everything said about the result:
what each piece is about ("Pause at 0:08.6 (3.00 s): marked intentional"), what it does,
its note, and Remove. A note (up to 280 characters) can be added to any entry there; that
is the one place notes are typed, so the controls in the tables stay a single click.

**When feedback moves a setting**, a notice appears in that section, with the reason the
backend wrote, the count ("3 of 3 reports agreed"), the confidence ("low"), and a link to
the calibration panel where it can be undone. It stays until dismissed.

How it is built:

| File | Role |
| --- | --- |
| `feedbackStore.ts` | A store of its own, in the same style as the others. Holds the feedback on the result on view, the calibration, and any adjustment just made. `watch(analysisId)` switches it to another result; `give`, `remove`, `undo`, `reset`, `setAdaptive` each send one request and take in the answer |
| `feedback.ts` | Pure helpers: which entry belongs to which pause or phrase, the silences inside a phrase, the gaps between its words and the silence nearest a moment, whether the labels have changed since the coaching was written, how a result's minimum pause is worded, the line beside the "ask the AI model" button |
| `FeedbackControls.tsx` | `PauseFeedbackSelect`, `SegmentReport`, `CorrectionRating`, `FeedbackEntry`, `WpmReviewView` |
| `FeedbackSection.tsx` | The gathered list and the adjustment notice |
| `useFeedback(analysisId)` | Connects the store to React and tells it which result is on view |

Every request that changes feedback or calibration is answered with the full, fresh list
and the full calibration, so the store never patches its copy: it replaces it. An answer
about a result the user has since left is dropped, except for its calibration, which
belongs to the whole app.

### 6.19 The calibration panel

At the bottom of the General Practice page, under the history, and at the bottom of the
Daily Practice page and of a take's own page: **Feedback and calibration**. It is there
whether or not a result is on view.

| Part | Shows |
| --- | --- |
| A badge | "Still calibrating", "Adjusted from your feedback" or "Automatic adjustment off" |
| One line | The settings version, how many pieces of feedback are stored, how many reports are waiting to count |
| A summary sentence | Written by the backend. While nothing has moved: "Still calibrating: every setting is at its default. A setting moves only after 3 reports that agree, from at least 2 different recordings, at least 1 of them about a take of your own. Reports waiting: 0." |
| A table | For each adjustable setting: its value now, its default, its allowed range, and where it stands ("At its default. 2 of the 3 reports needed for lowering it, from 1 of the 2 recordings needed."), with its confidence |
| Three controls | **Undo last adjustment**, **Reset to defaults** (asks first), and a tick box, **Adjust settings automatically from my feedback** |
| **What your feedback adds up to** | The counted facts, your notes, and the notes the AI model picked out (6.23) |
| Three fold-away parts | What changed, and why (every version, newest first, with its reason and counts) · How a setting gets adjusted (the rules, in words, including the one about reference recordings) · Thresholds that feedback never changes |

There are twelve "priority of corrections about …" settings. Listing all twelve at 1.0
would bury the one that matters, so only those with a rating waiting, or that have moved,
get a row; one sentence accounts for the rest.

The panel's opening text says what calibration is not: it "improves rules of thumb. It
does not retrain the speech recogniser, and it does not guarantee a perfect analysis."

### 6.20 Revisions, corrected transcripts and analysing again

A recording can have more than one result. Each is a complete result of its own, with its
own row in the history; the screen only has to say how they are related.

- **The header** of a result that has relatives says which it is ("Revision 2: transcript
  corrected") and lists the others as links.
- **Correcting the transcript** (`store.correctTranscript`): one request, answered at once
  with the new revision, which replaces the result on view. A notice says "Saved as
  revision 2. Word counts and WPM were worked out again from your words. The earlier
  result is still in your history, unchanged." The recording held in the page's memory
  plays for the new revision too; it is released only when neither result needs it.
- **Analysing again** (`store.reanalyse`): shown when the minimum pause has moved since a
  result was made. It starts a job that is followed in the run panel exactly like an
  upload, under the headings "Analysing the recording again" and "New revision ready". It
  needs the recording to have been kept; when it was not, the notice says so instead of
  offering the button.
- **A monologue's original** measured with older settings gets the same offer in step 1 of
  Daily Practice ("Measure the original again"). The new revision becomes the one takes
  are compared with; the earlier one is kept, and can be opened from the links in the
  header of step 1. The monologue is still one row in the list.

### 6.21 Accessibility of the feedback controls

- The pause control is an ordinary list box (`<select>`) named for its pause: "Your
  feedback on the pause at 0:08.6".
- "Report a problem" says which segment and whether its form is open (`aria-expanded`),
  and points at the form it controls. The form opens **below** the table, not inside it:
  the table scrolls sideways on a narrow screen, and a form must never need sideways
  scrolling to be read. Keyboard focus moves to the form when it opens.
- The choices in the form are radio buttons inside labelled groups.
- Useful and Not useful are toggle buttons that announce whether they are pressed, and
  name the correction they rate.
- Long notices carry their button under the text, so the text keeps the full width on a
  phone.
- Reset asks for confirmation in the same dialog as every other irreversible action, and
  focus returns to the button afterwards.
- The words to pick from are buttons in a group named "The word the pause came after".
  Each announces itself in full ("The pause came after “am”, word 7 of the phrase") and
  whether it is pressed. They are 44 px tall like every other control, and wrap onto as
  many lines as the phrase needs. The "‖ pause here" mark beside the pressed word is for
  the eye only; a screen reader is told by the pressed state.
- The line beside "Ask the AI model…" is a status region, so "Waiting for the worker…" and
  "The AI model is choosing" are announced as they change.

### 6.22 Feedback on a reference recording

Shown in step 1 of Daily Practice ("Listen and observe"), a monologue's original shows the
ordinary results view with a smaller set of the feedback controls:

| Where | On a take | On a reference |
| --- | --- | --- |
| Each pause | Intentional · Accidental · Not a pause: I was still speaking · Too short to split the phrase | Not a pause: someone is still speaking · Too short to split the phrase |
| Each phrase, "Report a problem" | A pause was missed · WPM too high · too low · The words are wrong | The same four |
| Coaching corrections | Useful · Not useful | None: a reference has no coaching |
| The gathered section | "Your feedback on this result" | "Your feedback on this reference" |

The two labels are missing because a label only changes how the coaching reads a pause,
and a reference has none. The backend refuses them too; the screen simply does not offer
them (`REFERENCE_PAUSE_CHOICES` in `feedback.ts`).

**Correcting a reference's words** is the part most likely to be used: a misheard word in
the reference spoils the line-up of every take compared with it. It works as on a take,
with three differences in what happens afterwards (`store.correctTranscript`):

- the corrected reference **becomes the one its monologue's takes are compared with**, so
  the comparison on screen, and the script in steps 2 and 3, are at once in the corrected
  words;
- the take on view stays on view;
- the notice says "Saved as revision 2 of the original recording… your takes are now
  compared with this revision. The earlier one is kept, unchanged."

The header of a reference with more than one revision says which it is and links to the
others; following a link chooses that revision as the reference.

**Reports on a reference** are saved and shown like any other. What differs is said in
words wherever it matters: under the pauses table, in the note at the foot of the gathered
section, in each report's own sentence ("All of them are about reference recordings, and
a setting moves only once a take of your own shows the same thing"), and in "How a setting
gets adjusted" in the panel.

How it is wired: there is one feedback store for the whole app, and it watches one
analysis at a time. On General Practice and on a take's own page that is the take on
view. On Daily Practice it is the original being studied
(`useFeedback(reference?.analysisId ?? null)`). The screens are never on view together,
so one store is enough.

### 6.23 What your feedback adds up to

A part of the calibration panel (`FeedbackSummaryPanel.tsx`), in three layers, each of
which works without the one below it:

```
 What your feedback adds up to
 • 12 pieces of feedback in all, on 3 recordings: 6 on your own takes and 6 on reference…
 • What it is about, largest group first: missed pauses (5), WPM figures (3), …
 • Missed pauses you reported: 5. At 5 of them the detector had heard a silence lasting
   between 324 and 356 ms, which was shorter than the minimum pause at the time…
 Counted by the app from your stored feedback, so it is always up to date. The AI model
 has no part in these lines.

 ┌ The most telling, as picked by the AI model ────────────────────────────────────────┐
 │ "yahan maine jaan-boojhkar ruka tha"              On a pause you said the app missed │
 │ "lost my place here"                              On a pause you labelled accidental │
 │ "feels slower than this when I listen back"       On a WPM figure you said the app…  │
 │ Picked from 10 notes by the AI model llama3.1:8b, running on this computer, on        │
 │ 11 Oct, 15:48 in 2.5 s. The model only chose: every word above is yours…              │
 └──────────────────────────────────────────────────────────────────────────────────────┘
 [ Ask the AI model to pick again ]   Optional. The local AI model is given your notes
                                      as text and nothing else, and only chooses…
 ▸ Your notes, as you wrote them (10)
```

| Layer | Comes from | Needs |
| --- | --- | --- |
| The facts | `GET /api/feedback-summary`, counted by the backend's code each time | Any feedback at all |
| Your notes | The same answer: the latest 15, word for word, each with what it was about | A note |
| The AI model's pick | A job started by the button | Five notes of three words or more, the worker, and Ollama |

The screen writes none of these sentences. It shows what the backend sent.

**The button** is off, with the reason beside it, when there are too few notes ("…once
there are at least 5 notes of a few words or more (there are 3)") or the AI model is not
available ("…not available right now: Ollama is not running. Nothing above depends on
it."). While the job is waiting or running the button becomes **Stop**, and the line
beside it follows the job. If the job fails, the reason is shown with the same help as a
failed coaching job (how to start Ollama, and so on), and the button reads "Try again".

**Out of date.** When a note is added, edited or removed after a pick, the box says "Out
of date: your notes have changed since these were picked", and goes on showing what was
picked. Feedback without a note changes the facts at once and leaves the pick current.

How it is built: the summary lives in `feedbackStore.ts`, beside the calibration, because
like the calibration it belongs to the whole app and not to one result.

| Action | Does |
| --- | --- |
| `loadSummary()` | Fetches the facts, the notes and the last pick. Called once when a screen with the panel opens |
| `askForSummary()` | Starts the job, then asks again every 2 seconds for as long as the answer says the job is queued or running |
| `cancelSummary()` | Cancels that job through the ordinary job endpoint, then fetches the summary again |
| after `give`, `remove`, `undo`, `reset`, `setAdaptive` | The summary is fetched again, because the facts are made from the feedback and the settings |

A request for the summary that is answered late cannot overwrite a newer answer: each
request carries a number, and only the answer to the latest one is used.

## 7. What is saved in the browser

Three `localStorage` keys, and nothing else:

| Key | Written by | Holds |
| --- | --- | --- |
| `monologue-coach.practice.v1` | Daily Practice | All saved checklist days, as JSON: each day's steps, the monologue its round is on, and the rounds finished earlier that day |
| `monologue-coach.general.active-job` | Daily Practice, Monologues, General Practice | The ID of an analysis still in progress, so a refresh can pick it up. Removed when the job ends |
| `monologue-coach.voice-goal` | The recording form (Phase 9) | `lower` or `higher`: the voice goal last chosen. Not written at all for "No goal" |

Another key, `monologue-coach.reference.selected`, was written until Phase 8: it
remembered which reference was chosen. The monologue being practised now says which
reference is meant, so the key is no longer written, and is removed the first time the
app opens.

The checklist's value looks like this:

```ts
{ schemaVersion: 1, days: { "2026-10-10": { ...record }, "2026-10-11": { ...record } } }
```

The monologue screens and General Practice save **no results and no audio in the browser**. Feedback
and calibration are not saved in the browser either: both live in the backend's database,
so they are the same whichever browser the app is opened in. The
monologues, their original recordings and their takes are in the backend's database and data folder, not here. Results live in the
backend's database. A recording you just made or chose is held in the page's memory so it
can be played back with its result; it is gone when the tab is closed or refreshed, unless
you ticked "Keep this recording", in which case the backend stores it.

Things to know about `localStorage`:

- It belongs to one browser on one device. Chrome and Safari each have their own copy, and so
  does a private window. Nothing syncs.
- Clearing the browser's site data deletes it.
- It also depends on the address: `http://localhost:1234` and `http://localhost:1235` are
  different sites to the browser and do not share data. That is why the development server
  has a fixed default port (decision F16). If port 1234 is ever taken and Next.js picks
  another, the checklist history saved under 1234 will not be visible there.

You can look at the saved data in the browser's developer tools: Application (or Storage) →
Local Storage → the site's address.

## 8. Frontend decisions

Each entry says what was chosen, what was considered, and what was decided against and why.

### F1. System fonts instead of Google Fonts

- **Chosen:** the fonts already on the device.
- **Why:** the Next.js starter downloads fonts from Google when the app is built. A
  local-first app should build and run with no network.
- **Decided against:** `next/font/google`.

### F2. Checklist data lives in the browser (`localStorage`), not in the database

- **Chosen:** `localStorage`.
- **Why:** the checklist then needs no backend and makes no network requests at all, which
  the requirements ask for. It works even when the Python server is not running.
- **Decided against:**
  - *Saving through the API into SQLite:* the requirements say to reuse a backend store if
    one exists, but when the checklist was built the database had no tables, and this would
    make a simple timer page depend on a second program being up.
  - *IndexedDB:* a bigger browser database; unnecessary for a few kilobytes.
- **Trade-off accepted:** data is tied to one browser and one address (see section 7), and
  the backend cannot see it. If checklist history should one day sit next to the analyses in
  SQLite, an import step will be needed.

### F3. The timer stores an end time instead of counting down

- **Chosen:** store `endsAtEpochMs`; work out the time left from the clock.
- **Why:** it stays correct through background tabs, refreshes and a sleeping laptop.
- **Decided against:** subtracting one each second with `setInterval`. It drifts, stops in
  background tabs and is lost on refresh.

### F4. One timer, belonging to the current step

- **Chosen:** a single timer. Switching to another step stops it.
- **Why:** there can never be two countdowns running, and the state stays small.
- **Decided against:** a separate timer per step, each remembering its own paused time. More
  state and more ways to go wrong, for a routine that is done one step at a time.
- **Trade-off accepted:** if you pause step 2 and switch to step 4, step 2 goes back to its
  full time.

### F5. Rules as plain functions, state in a small hand-written store

- **Chosen:** `practiceState.ts` (pure functions) plus `practiceStore.ts`, connected to
  React with the built-in `useSyncExternalStore` hook.
- **Why:**
  - The rules can be tested without a browser, with a fake clock and fake storage.
  - The server that pre-renders the page cannot see your browser's saved data, so the page
    must first show "Loading" and then the real state. `useSyncExternalStore` is designed for
    exactly that.
  - One store per page load means remounting a component cannot create a second timer.
- **Decided against:**
  - *`useState` + `useEffect` inside the component:* logic gets mixed into the page, is hard
    to test, and the project's lint rules flag setting state inside effects.
  - *Redux or Zustand:* a new dependency for one small feature.

### F6. Skipped is not completed

- **Chosen:** three distinct states. Progress and "full routine" count completed steps only.
- **Why:** the history should be honest. A day with three skips is not a 100% day.
- **Decided against:** treating skip as "done", or hiding skipped steps.

### F7. The next step never starts by itself

- **Chosen:** when a timer ends, the next step becomes current and waits.
- **Why:** required, and you may need a moment between steps (finding the clip, getting up).
- **Decided against:** auto-starting the next countdown.

### F8. Days with no progress are not saved

- **Chosen:** a day is written only once something has happened. When nothing at all is
  left, the storage key is removed.
- **Why:** otherwise opening the page each day would fill the history with "0 of 5".
- **Decided against:** creating a record every day the page is opened.

### F9. A new day starts at local midnight

- **Chosen:** local calendar date; a running timer may finish and counts for the day it
  started; a paused timer is dropped.
- **Decided against:** the UTC date (wrong day for part of every day outside UTC); a custom
  cut-off such as 4 am (harder to explain); carrying a paused timer into the new day (a
  timer paused yesterday would hold yesterday open indefinitely).
- **Trade-off accepted:** if you practise across midnight and pause after 12:00, the fresh
  checklist appears at that moment.

### F10. Damaged saved data never crashes the page

- **Chosen:** check everything on load, keep what is valid, repair what is repairable, show
  a message that does not block the page.
- **Decided against:** trusting saved data (one bad value could break the page for good);
  silently wiping everything on any error.

### F11. Confirmation pop-ups use the browser's own `<dialog>`

- **Chosen:** the native `<dialog>` element.
- **Why:** it handles keyboard focus and the Escape key correctly without extra code.
- **Decided against:** `window.confirm()` (cannot be styled and freezes the page, including
  the timer display); a modal library (a dependency for two pop-ups).

### F12. Unavailable buttons stay focusable

- **Chosen:** buttons are marked `aria-disabled` and ignore clicks, instead of using the
  `disabled` attribute.
- **Why:** pressing Start switches Start off. With the `disabled` attribute, a keyboard user
  would lose their place on the page at that moment.
- **Decided against:** the plain `disabled` attribute.

### F13. Tests target the logic; the screens are checked by hand

- **Chosen:** Vitest tests for the rules and the store; the page itself was checked by
  clicking through it in a browser.
- **Why:** the hard parts (time, saving, day changes) are all in the logic.
- **Decided against (for now):** component tests with a simulated browser. They need more
  dependencies and would mostly repeat what the logic tests cover. They can be added later.

### F14. "Record and compare" links to what exists, and says what does not

- **Chosen:** step 4 of the checklist links to General Practice, which records and measures
  your own take, and says plainly that comparing it side by side with the original is not
  built yet.
- **Why:** a link to a page that is not there, or a button that pretends to work, would be
  misleading.
- **Since Phase 5:** the comparison exists, so step 4 linked to the Monologue screen, and
  so did step 1 ("Listen and observe"), where the original can be played and its measured
  pauses and pace read. Step 1's note still says what is left to the ear: breathing, and
  emphasis made by slowing down, are not measured.
- **Since Phase 8:** the steps link nowhere. What each one needs is underneath it
  (decision F69).

### F15. Styling with Tailwind CSS

- **Chosen:** Tailwind utility classes, which came with the Next.js starter.
- **Why:** no extra setup, and styles sit next to the markup they affect.
- **Decided against:** a ready-made component library (heavier, and its look would need
  overriding); separate hand-written CSS files per component.

### F16. A fixed port for the development server

- **Chosen:** `npm run dev` starts on port 1234 unless told otherwise. The API's commands
  use port 4321, and that is the address the frontend calls by default.
- **Why:** the browser stores saved data per address. Port 3000 was already in use on this
  machine, so the server would start on whichever port happened to be free, and checklist
  data saved under one port is invisible under another. A fixed port keeps the address
  stable. The two numbers themselves are the user's choice.
- **Decided against:** leaving it to chance (3000, 3001, 3002…); moving the checklist's data
  to the backend just to escape this.
- **Changed once:** the defaults were 3210 (frontend) and 8000 (API) until the user asked
  for 1234 and 4321. Checklist history saved while the app ran on port 3210 is still in the
  browser under that address and does not show on port 1234. To see it again, run
  `PORT=3210 npm run dev`.

### F17. The same store pattern as the checklist

- **Chosen:** `generalStore.ts`, `recorder.ts` and `healthMonitor.ts` are plain objects with
  `subscribe` and `getSnapshot`, connected to React by `useSyncExternalStore`. Their
  dependencies (backend client, timer, microphone) are passed in.
- **Why:** the hard parts — polling, back-off, retries, cancelling, a microphone that says
  no — can then be tested by scripting those dependencies. One store per page also means a
  remounted component cannot start a second recording or a second polling loop.
- **Decided against:** a data-fetching library such as React Query or SWR (good at caching
  requests, but the job state machine and the recorder would still need writing, and it is
  another dependency); state inside components (hard to test, easy to duplicate timers).

### F18. Polling once a second, slowing down when the backend is silent

- **Chosen:** one check per second; 2 s, 4 s, then 5 s between checks while the backend does
  not answer.
- **Why:** a job changes state about five times in half a minute, so once a second feels
  immediate and costs almost nothing. Backing off avoids hammering a backend that is down.
- **Decided against:** a tight loop; a fixed slow interval (the screen would lag behind the
  stages); a push connection (see backend decision B8).

### F19. Stages are shown, never a percentage

- **Chosen:** the stages (five since Phase 4, when "Writing the coaching" was added) with
  done / in progress / waiting.
- **Why:** the backend knows which stage it is in. It does not know that it is "62% done",
  and a made-up bar that crawls or jumps teaches people to distrust it.

### F20. A job in progress is remembered across a refresh

- **Chosen:** the job's ID is kept in `localStorage` while it is in progress.
- **Why:** an analysis can take a while; an accidental refresh should not lose it.
- **Decided against:** asking the backend for "any job in progress" (it would also pick up
  jobs from other tabs or sessions and guess which one is yours).

### F21. Profiles, languages and limits come from the backend

- **Chosen:** the form is built from `GET /api/analysis-options`.
- **Why:** the profile descriptions will also be used by the AI coaching step. Kept in one
  place, the screen and the coaching can never drift apart; and the size and length limits
  shown are the ones actually enforced.
- **Decided against:** copying the texts and limits into the frontend.

### F22. Recording with the browser's MediaRecorder, sent as recorded

- **Chosen:** `MediaRecorder`, in whatever format the browser offers (WebM or MP4).
- **Why:** it is built in, needs no library, and produces small files. The backend decodes
  both formats.
- **Decided against:** capturing raw samples and encoding WAV in the page (large files and
  more code, for audio that is immediately decoded again); a recording library (a
  dependency wrapping the same browser feature).
- **Trade-off accepted:** such recordings carry no length, which needs the fix in F23.

### F23. Unknown length is fixed by asking the browser to seek past the end

- **Chosen:** the well-known jump-past-the-end remedy, in `audioDuration.ts`.
- **Why:** without it, a browser-made recording cannot be seeked, so playing a single
  segment does nothing. This was found while testing, not anticipated.
- **Decided against:** rewriting the file's header in the page (needs a library that
  understands the WebM format); decoding and re-encoding the recording (slow, and uses a lot
  of memory for long recordings).
- **Trade-off accepted:** the browser reads through the recording once when the player loads.

### F24. Files are checked in the browser and again in the backend

- **Chosen:** quick checks before sending; the backend repeats them and has the final say.
- **Why:** an obviously wrong file gets an answer at once, without an upload. The browser's
  checks are a convenience, not a safeguard, because they can be bypassed.

### F25. The chart is hand-drawn SVG, in one colour, on two panels

- **Chosen:** a small SVG component with no charting library.
- **Why:** it is one line and a row of bars. A library would be a large dependency for that,
  and the choices that matter here — fitting labels or leaving them out, the hover readout,
  keyboard use — are easier to control directly.
- **Decided against:**
  - *A charting library* such as Recharts or Chart.js.
  - *Colouring segments by pace* (for example red for fast): colour would then carry a
    judgement the app is not making, and red reads as "wrong". Faster and slower are marked
    with ▲ and ▼ and spelled out in the table instead.
  - *One panel with two y-axes* for loudness and speech: see 6.10.

### F26. Comparison shows the change, not a verdict

- **Chosen:** signed differences only.
- **Why:** "slower" is better for one performance and worse for another. Judging needs the
  profile and the speaker's intent, which is the coaching step's job (Phase 4).
- **Decided against:** green/red arrows or "improved" labels.

### F27. The recording stays in memory unless you ask to keep it

- **Chosen:** audio is held in the page for the session, so results can be listened to;
  "Keep this recording" is off by default.
- **Why:** it gives playback without storing anyone's voice on disk unasked.
- **Decided against:** always storing audio; never allowing playback.
- **Trade-off accepted:** after a refresh, an analysis whose recording was not kept has no
  audio to play.

### F28. Coaching is a labelled gap, not a mock-up *(Phase 3; replaced in Phase 4)*

- **Chosen in Phase 3:** the results showed which measurements the profile depends on, and
  a note that corrections and drills would arrive with AI coaching.
- **Decided against then:** placeholder "tips" dressed up as coaching, which would have
  looked finished while nothing stood behind them.
- **Now:** the gap is filled (F30 to F35). Coaching from fixed rules does exist in Phase 4,
  but it is built on the same findings as the AI coaching, and it is labelled as what it is.

### F29. The end of a segment is watched every frame, with a fallback

- **Chosen:** check playback position on each animation frame, and also on the audio
  element's own time events.
- **Why:** the time events arrive only about four times a second, which overshoots a short
  phrase by up to a quarter of a second. Frame checks are precise but pause in a background
  tab, where the time events still arrive.

### F30. Every correction shows what was measured, beside what the coach says

- **Chosen:** three labelled parts in each correction: **Measured** (the finding, written
  by code), **Why it matters** and **Drill** (the coach's words), and **Practise on** (the
  phrase, with Play).
- **Why:** it lets you judge the advice. If the coach says "slow down" you can see the 240
  WPM it rests on, and hear the phrase, without taking anything on trust.
- **Decided against:** one paragraph per correction with the figures woven into the prose.
  It reads more naturally, but you could no longer tell a measured figure from the model's
  wording.

### F31. The practice phrase is looked up in the transcript, not taken from the coach

- **Chosen:** the backend sends only which segment to practise on; the screen shows that
  segment's own words and times.
- **Why:** an AI model can misquote. The words under "Practise on" are therefore always
  exactly what the speech recogniser heard, and Play always plays exactly that stretch.

### F32. Who wrote the coaching is always stated

- **Chosen:** a line at the top of the section says whether the AI model or fixed rules
  wrote it; for the AI model, that it ran on this computer and was never given the audio;
  for rules, why the model was not used and how to fix that.
- **Why:** the two are different things with different weaknesses. A model can be fluent and
  wrong; templates are safe and generic. The reader should know which they are reading.
- **Decided against:** showing both the same way, or a small "AI" badge that explains
  nothing.

### F33. Coaching sits near the top of the results

- **Chosen:** directly under the recording and its chart, above the Pace, Pauses and Voice
  tables.
- **Why:** it answers "what should I do next?", which is why someone records a take. The
  tables are the evidence, for anyone who wants to check.
- **Decided against:** leaving it below the tables, where it sat as a placeholder in Phase
  3, a long scroll away.

### F34. Writing the coaching again reuses the run, not a second mechanism

- **Chosen:** `regenerateCoaching()` starts an ordinary run of a different kind. Polling,
  back-off, cancel, resume after refresh and "one at a time" all come from the code that
  already follows an analysis.
- **Why:** a second, parallel tracker would be a second copy of the trickiest logic in the
  store, and would allow two jobs to be in progress at once.
- **Decided against:** a separate small state machine just for coaching.
- **Cost accepted:** only one thing can be in progress, so the button is switched off while
  an analysis is running.

### F35. The AI model being unavailable is a notice, not an error

- **Chosen:** an ordinary notice at the top of the screen, and a disabled button with the
  reason beside it. Nothing is blocked.
- **Why:** everything except the wording of the coaching still works, and saying so plainly
  is more useful than a red box.
- **Decided against:** hiding the Coaching section when the model is unavailable (the
  rule-based coaching is still worth reading), and treating it like a missing worker (which
  really does stop everything).

### F36. One store for both screens

- **Still true after Phase 8**, for more screens: Monologues, Daily Practice, a take's page
  and General Practice all share it. What changed is that the screens no longer show the
  same things, so each one takes from the store only what belongs to it (decision F74).
- **Chosen:** General Practice and Monologue share the single store created in
  `useGeneralPractice.ts`.
- **Why:** they show the same things: the same takes, the same references, the same run in
  progress. With one store, a reference chosen on one screen is chosen on the other, a job
  started on one is followed on the other, and there is one place where "only one run at a
  time" is enforced.
- **Decided against:** a second store for the Monologue screen. Two stores following jobs
  would be two copies of the trickiest code, and could each start a run.

### F37. The comparison follows what is on screen; there is no "Compare" button

- **Chosen:** the store fetches the comparison whenever the take on view or the chosen
  reference changes.
- **Why:** it takes a few thousandths of a second, so there is nothing to wait for and
  nothing to confirm. It also means no component can forget to ask, and two components
  cannot ask for different pairs.
- **Decided against:** a button (a step with no purpose), and fetching from inside a
  component when it appears (the same request from two places, on two screens).

### F38. The Monologue screen reuses the results view, and links to General Practice for the rest

- **Changed in Phase 8.** The results view is still reused, twice: for the original in
  step 1, and for a take on its own page. But a take's full results are no longer in
  General Practice: they have a page under Monologues (decision F73).
- **Chosen in Phase 5:** the reference is studied in the ordinary results view with a `mode` that
  hides what does not apply. A take's full results stay in General Practice, one link away.
- **Why:** a second results view would have to be kept in step with the first for ever. The
  Monologue screen can stay about one question: where does my take differ from the original?
- **Decided against:** showing the take's full results, coaching and all, on the Monologue
  screen as well: a very long page that says the same thing in two places.

### F39. A reference is kept by default; a take is not

- **Chosen:** "Keep this recording on this device" starts ticked when adding a reference,
  and unticked for a take, with the reason written beside each.
- **Why:** a take is usually listened to once, and the brief says not to store raw audio
  indefinitely by default. A reference is added precisely to be played and compared against
  on other days, and without its audio the listen buttons and the daily "listen and
  observe" step have nothing to play. The choice is still visible and the user's.
- **Decided against:** off for both (a reference that goes silent on the next visit), and
  keeping a reference without asking.

### F40. The waveform is off by default and fetched only when switched on

- **Chosen:** a checkbox, unticked each time; the outlines are requested when it is ticked.
- **Why:** it is a visual aid some people want and many do not. Leaving it off costs
  nothing: no request, no drawing. It also keeps a picture that proves nothing out of the
  way of the figures that do.

### F41. The two waves are never lined up automatically, and each keeps its real length

- **Chosen:** both start at zero; a shift is a number the user types and can see; the
  shorter recording simply ends earlier.
- **Why:** lining them up by machine would assert that a moment in one corresponds to a
  moment in the other. The comparison does establish that, through the words; a picture
  shifted by eye must not look as if it did. Stretching one to the other's length would
  falsely suggest they took the same time.
- **Decided against:** auto-alignment, and scaling both to the same width.

### F42. One above the other by default; overlaid on request

- **Chosen:** two lanes sharing a time axis, with "Overlaid" as an option.
- **Why:** two dense shapes on top of each other are hard to tell apart even in two
  colours, and the pauses, which are what one looks for, are easiest to compare when each
  wave has its own lane. Overlaying is still there for anyone who wants it.

### F43. Both waves share one scale unless the user asks otherwise

- **Chosen:** full height means the loudest a recording can be, for both. "Stretch each to
  its own loudest point" is an explicit option that says what it hides.
- **Why:** a quiet recording drawn as tall as a loud one would imply they were equally
  loud. The honest default is that a quiet recording looks thin; the option exists because
  a thin shape is hard to read.

### F44. Every difference can be heard in both recordings

- **Chosen:** each difference, each pause row and each phrase row has **Reference** and
  **Yours**, playing that spot in each, a pause with a second and a half either side.
- **Why:** the checklist's first step is "listen and observe". A table that says the
  original holds 1.6 seconds where you held 2.6 is far more useful when both can be heard
  one after the other.
- **Decided against:** one shared player that switches recordings (it loses your place in
  both).

### F45. An element's width is measured through a callback, not a ref object

- **Chosen:** `useElementWidth` is handed its element by a callback.
- **Why:** found in the browser. The waveform chart shows "loading" first and draws its
  chart area only once the outlines arrive. The first version attached its size watcher
  when the component appeared, found no chart area yet, and never looked again, so the chart
  stayed zero pixels wide and blank. A callback is told when the element appears, whenever
  that is.

### F46. Feedback controls sit beside the thing they are about

- **Chosen:** a list on each pause, "Report a problem" on each phrase, two buttons on each
  correction. No separate feedback form.
- **Why:** the brief asks that the user can select "the exact timestamp, pause, segment…
  or coaching suggestion", and asks for feedback to be quick. Beside the row, the target
  is already chosen: one click says everything.
- **Decided against:** *a feedback page with menus for "which pause"*: the user would have
  to find in a menu what they are already looking at. *A free-text box as the main way*:
  the brief asks for structure, and text cannot be counted towards a setting.

### F47. The backend writes the sentence that says what feedback does

- **Chosen:** every saved piece of feedback comes back with a `message`, and the screen
  shows it as it is.
- **Why:** what a report does depends on rules and counts that live in the backend ("2 of
  the 3 reports needed, from 1 of the 2 recordings needed"). A second copy of that logic in
  the browser would sooner or later say something different.

### F48. Feedback and calibration have a store of their own

- **Chosen:** `feedbackStore.ts`, beside `generalStore.ts`, in the same style.
- **Why:** the general store's job is following jobs and deciding what is on view. Feedback
  has no jobs: each action is one request. Mixing them would have made a 900-line store
  that does two unrelated things.
- **How the two meet:** only through the page, which tells the feedback store which result
  is on view. Neither store calls the other.

### F49. Every answer replaces the list; nothing is guessed in advance

- **Chosen:** after any change the backend returns the whole list of feedback and the whole
  calibration, and the store swaps them in.
- **Why:** one piece of feedback can change the sentence on several others (a third report
  turns two "waiting" entries into "counted in version 2"). Patching the local copy would
  mean re-implementing the backend's rules.
- **Decided against:** *showing the change before the backend confirms it*. A local
  request takes a few milliseconds, and a control that shows "saved" before it is saved
  can be wrong.

### F50. A pause is labelled from a plain list box, saved on choosing

- **Chosen:** a native `<select>` per pause, with no separate Save button.
- **Why:** four choices of which only one can hold, in a table row with little room. A list
  box is one control, works by keyboard and screen reader without extra code, and makes it
  impossible to pick two.
- **Decided against:** four buttons per row (crowded on a phone, and they would need their
  own "only one at a time" logic).

### F51. A missed pause is pointed at by choosing a silence the app measured

- **Chosen:** the form lists the short silences the detector heard inside the phrase, with
  the word each follows and a play button. The playhead position and "I cannot say" are
  the other two choices.
- **Why:** typing a time such as "2.6" is slow and usually wrong by a few tenths. Choosing
  from what was measured is quicker and gives the backend an exact silence to check the
  report against.
- **Decided against:** *clicking on the timeline chart to mark the spot*: precise with a
  mouse, hard with a keyboard, and the chart is far up the page from the phrase.
- **Not built then; built in Phase 7:** choosing a single word in the transcript as the
  place (decision F61).

### F52. The phrase form opens under the table, not inside it

- **Chosen:** "Report a problem" marks its row and opens the form below the whole table.
- **Why:** found in the browser. The first version put the form in a row of the table. The
  table scrolls sideways on a narrow screen, so the form did too, and its text ran off the
  edge. A form must never need sideways scrolling.
- **Detail:** focus moves to the form when it opens. The function that does this is kept
  the same between redraws; otherwise it would run again several times a second while the
  recording plays, and pull the cursor out of the text box.

### F53. Notes are typed in one place

- **Chosen:** any saved piece of feedback can be given a note in the "Your feedback on this
  result" list. The controls in the tables have no note box.
- **Why:** the brief asks for an optional short note and for feedback to stay quick. A note
  box on every row would make every row slower for the sake of the few that get a note.

### F54. Only the priorities that something has happened to get a row

- **Chosen:** the calibration table always shows the minimum pause. Of the twelve
  correction priorities, it shows those with a rating waiting or a changed value, and one
  sentence accounts for the rest.
- **Why:** twelve identical rows saying "1.0, at its default" would hide the one that
  differs. Nothing is concealed: the sentence gives the value and range the others share.

### F55. "Still calibrating" and "low" are said in words, and an adjustment is announced

- **Chosen:** a badge names the state; each setting's confidence is a word with the count
  beside it; and when feedback moves a setting, a notice says what moved, why, on how many
  reports, and where to undo it.
- **Why:** the brief says not to claim the app has learned from a few noisy events, and to
  avoid settings changing "without notice". A change that only showed in a table at the
  bottom of the page would be exactly that.

### F56. Reset asks first; undo does not

- **Chosen:** Reset opens the confirmation dialog. Undo acts at once.
- **Why:** undo reverses one step and can be made good by giving the feedback again. Reset
  discards every adjustment and every waiting report, and cannot be undone.

### F57. A new revision replaces the result on view

- **Chosen:** after a transcript correction, or when a fresh analysis finishes, the new
  revision is shown, with links to the others in its header.
- **Why:** it is what the user just asked for. The earlier result is one click away and
  still in the history.
- **If the user has moved on:** a correction that returns after another result was opened
  does not pull them back.

### F58. The minimum pause is read from the result, never assumed

- **Chosen:** every sentence that mentions the shortest pause ("silences of half a second
  or more") takes the figure from the result's own settings.
- **Why:** before Phase 6 the screen could say "half a second" as a fixed phrase. Now a
  result may have been made at 400 ms, and a fixed phrase would be untrue for it.

### F59. Feedback is given in General Practice; the Monologue screen links to it

- **Replaced.** Phase 7 put feedback on a reference where the reference is studied (F64),
  and Phase 8 gave a monologue's take a page of its own, where its feedback is given (F73).
- **Chosen in Phase 6:** the Monologue screen shows the comparison only, as before, and its link to
  General Practice now says feedback is given there.
- **Why:** the brief places the feedback and calibration panel in General Practice, and the
  controls live in the full results view, which the Monologue screen already hands over to
  General Practice (decision F38).

### F60. With new labels, "write the coaching again" works without the AI model

- **Chosen:** normally the button is off when the AI model is unavailable. When pause
  labels have changed since the coaching was written, it is on, and the line beside it
  says the coaching will be rewritten from the fixed rules with the labels taken in.
- **Why:** it mirrors the backend (decision B51). Otherwise a user without Ollama could
  label pauses and never see the labels reach their coaching.

### F61. Words to pick from are buttons, and the last word is not one

- **Chosen:** each word of the phrase is a toggle button; pressing it means "the pause
  came after this word". The last word is plain text.
- **Why:** a pause sits between two words, so there is one place fewer than there are
  words. Making the last word a button would offer a place that is not inside the phrase:
  the silence after it is the pause that ended the phrase.
- **Decided against:** *markers between the words to click on* (a target a few pixels wide,
  and nothing for a keyboard to land on); *a text box to type the word into* (a phrase can
  say the same word twice).

### F62. The screen previews what the detector heard, with the backend's own rule

- **Chosen:** when a word is picked, the screen says which silence the report will be
  about, using a copy of the backend's rule (the nearest silence within half a second).
- **Why:** word times come from the speech recogniser and can be a fraction of a second
  out, so "after this word" may land beside a silence and not on it. Showing which silence
  it will be taken to mean lets the user see that before saving, and press Play to check.
- **The cost, and how it is contained:** the rule exists in two places. The backend's
  decides; the screen's only shows. `NEAR_SECONDS` in `feedback.ts` names the constant it
  copies, and a test pins the half second.
- **Decided against:** saving first and showing the backend's sentence afterwards (the
  user finds out what they reported only once it is stored).

### F63. Recognised words are shown without their punctuation, and Devanagari is kept whole

- **Chosen:** `bareWord` strips punctuation from both ends of a word before it is shown on
  a button or in a sentence.
- **Why:** the recogniser returns "name," and "Skyler." as words. On screen that gave
  `Between “my” and “name,”, at about…`.
- **A fault the test caught:** the first version removed everything that is not a letter
  or a digit, which turned "रुको" into "रुक": a Devanagari vowel sign is a *mark*, not a
  letter, and it was being cut off the end of the word. Marks now count as part of the
  word. The test with a Hindi word was written before the function was used anywhere.

### F64. A reference gets its feedback on the Monologue screen, from the same components

- **Since Phase 8** the place is step 1 of Daily Practice, which is where the original is
  now studied. The components and the reasoning are unchanged.
- **Chosen:** the results view already used for studying a reference takes the feedback
  controls, with a flag that changes the choices offered and the wording.
- **Why:** the place where a wrong word or a missed pause in the reference is noticed is
  where the reference is being studied. A second set of components for references would
  have drifted from the first.
- **Decided against:** opening references in General Practice (that screen's history,
  coaching and "compare with an earlier attempt" are all about takes).

### F65. The calibration panel is on both screens

- **Since Phase 8** it is on three: Daily Practice, a take's own page, and General
  Practice. Each is a page on which feedback can be given, for the same reason as below.
- **Chosen:** the same panel at the bottom of the Monologue page as at the bottom of
  General Practice.
- **Why:** feedback can now be given on the Monologue page, and when it moves a setting
  the notice links to the panel. A link to something on another page would be a dead end.

### F66. The AI model's pick is followed by the feedback store, not by the run panel

- **Chosen:** `feedbackStore.ts` starts the job and asks after it itself. The run panel,
  which follows analyses and coaching jobs, knows nothing about it.
- **Why:** the run panel is about the recording being worked on, and holds the screen's
  one "a run is in progress" state, which switches off the Analyse buttons. Picking notes
  takes a few seconds and is about no recording. Running it through the panel would have
  greyed out the whole form for it.
- **What it costs:** a second, much smaller, polling loop. It has no back-off and no
  resume-after-refresh, and needs neither: the first answer after a refresh says whether a
  job is still under way, and the loop picks up from there.

### F67. The pick is shown as the notes themselves, marked when it is out of date

- **Chosen:** the box shows the picked notes word for word, with what each was written
  about, the model's name, the time and how long it took. Once the notes change, it says
  so and still shows the pick.
- **Why:** it is the user's own text, so there is nothing to mistrust in it; and an
  out-of-date pick is still a true record of what was picked from what.
- **Decided against:** hiding an out-of-date pick (the user would wonder where it went);
  picking again automatically (the model's time is the user's to spend).

### F68. Daily Practice is done on a monologue, chosen from a list

- **Chosen:** the Monologue screen became a list of monologues; "Practise" on one opens
  Daily Practice for it. See decision G13 in the main document for why the two were
  joined.
- **Why a list first:** the user said how they think of it: pick the monologue, then
  practise. A routine with nothing to practise on has nothing to listen to in step 1.
- **Decided against:** *a menu of monologues at the top of Daily Practice.* It reads as a
  filter that can be flipped at any time, and flipping it mid-round is exactly what a
  round should not allow (F71). *Opening the last monologue automatically:* see F72.

### F69. Each step carries its tools, and they stay open while in use

- **Chosen:** the original, the script, the recorder and comparison, and the biggest
  differences sit under the step they belong to. A step's tools are open while it is the
  current step, while something of theirs is going on, or because the user opened them.
- **Why under the steps:** the step's instruction and the thing it is done with are then
  in one place, and the page reads top to bottom as the routine.
- **Why "while in use":** found by thinking through the timer. Step 4 is three minutes; a
  recording plus its analysis can outlast it. If the tools belonged strictly to the
  current step, the recorder would vanish mid-analysis when the timer ran out.
- **Why this is worked out and not stored:** "open" is a fact about the moment (which step
  is current, is a job running), so it is computed when the page is drawn. Only the
  user's own Show and Hide presses are kept, and only until the next round.
- **Decided against:** *one tools area for the current step only* (the problem above);
  *all five always open* (a very long page, with two copies of the script);
  *stopping the timer while an analysis runs* (the timer would then mean something
  different in one step than in the others).

### F70. One round is the day's routine; more are extra, and stay in the same day

- **Chosen:** "Practise again" files the finished round under `earlierRounds` and starts a
  fresh one. The history shows one row per day, with the figures of the best round.
- **Why:** the user asked for exactly this: one round a day is what counts, and a second
  should be possible. Keeping every round in the day's record means the first is not
  thrown away to make room for the second.
- **Decided against:** *"Reset today" as the way to practise again* (it erases the round
  that was just finished); *one history row per round* (seven days would no longer be
  seven rows); *a checklist per monologue per day* (the user chose one routine a day).
- **A consequence in the rules:** "all five completed" used to be read from the steps on
  screen alone. With rounds, the day's routine is done if *any* round was full, which
  `summarizeDay` works out. The round on screen is summarised on its own, as before.

### F71. A round stays on its monologue; switching is asked for

- **Chosen:** once anything has been done in a round, another monologue in the address
  does not move it. A notice offers to carry on or to switch, and switching asks first.
- **Why:** a round's steps are about one piece: the original listened to in step 1 is the
  one the take in step 4 is compared with. A round that changed monologue half-way would
  be recorded as practice of the wrong one.
- **Where the rule lives:** in `setMonologue`, with the other rules, where it is tested
  without a browser. The page only shows what the rule decided.
- **Decided against:** *switching silently* (three completed steps would be credited to a
  monologue they were not done on); *refusing with no way out* (the user may simply have
  started on the wrong one).

### F72. Choosing a monologue is not progress, and none is remembered between days

- **Chosen:** a monologue chosen with nothing done leaves nothing in storage. With no
  monologue in the address and none in today's record, the page shows the list to choose
  from, the one practised most recently first.
- **Why:** decision F8 says a day with no progress is not saved, and opening a monologue
  to look at it is not progress. Remembering "the last monologue" would need a second
  thing in storage that can go stale (the monologue may have been deleted), to save one
  click on a list that already puts the likeliest choice first.
- **Decided against:** *saving the chosen monologue as soon as it is chosen* (the history
  would fill with days on which nothing was practised); *a separate "last monologue" key.*

### F73. A take of a monologue has a page of its own, under Monologues

- **Chosen:** `/monologue/take?analysis=<id>`: the full results view for one take, with
  the comparison against the original inside it. Step 4 shows the comparison and a few
  headline figures, and links here.
- **Why:** the user asked for the comparison in the step and the rest one link away, and
  for that link not to lead into General Practice, which is now for speaking that has no
  original. The page reuses `Results` whole, so nothing about a result is drawn twice.
- **Decided against:** *the full results inside step 4* (coaching, four tables and the
  feedback controls under a three-minute step); *a new "Analyses" tab listing every
  result* (a second way to reach the same takes, away from their monologue).

### F74. Each screen shows only what belongs to it, though the store is shared

- **Chosen:** Daily Practice treats a take as on view only if it was recorded for the
  monologue being practised. A take's page shows only a take of a monologue. General
  Practice shows only a recording that belongs to none, and says so, with a link, when
  the store is holding something else.
- **Why:** the shared store (F36) holds one result "on view" for the whole app. After
  Phase 8 the screens are about different things, so each has to ask "is this mine?"
  before showing it. The check is one line in each page, next to where the result is read.
- **Decided against:** *a store per screen* (each would need its own job tracking, and
  two could start a run at once); *clearing what is on view whenever a screen opens* (a
  take being analysed would be lost by looking at another page).

### F75. The store is told which monologue the screen is about, and chooses its original in the same step

- **Chosen:** `watchMonologue(id)`. The store then loads the takes, chooses the newest
  reference, and keeps the comparison up to date.
- **Why one call:** before Phase 8 the chosen reference was a choice the user made from a
  menu and the store remembered. Now it follows from the monologue, so it should not be
  possible to have one without the other.
- **A fault the test caught:** the first version changed the monologue and then, a line
  later, the reference. In between, the comparison was brought up to date, and a take was
  for one request set against the *previous* monologue's original. A test written to
  check "never compared with another monologue's original" counted two requests where one
  was expected. Both now change in a single step.
- **Decided against:** *each page fetching its own reference and takes* (two pages, two
  copies, and the comparison would not know when either changed).

### F76. The script shows what was measured and nothing else

- **Chosen:** `buildScript` rearranges the original's stored result: its phrases, its
  pauses, its emphasis candidates. No new judgement is made.
- **Why:** step 2 asks the actor to mark the delivery. A script that suggested marks of
  its own would be coaching the original, which nobody asked for and nothing measures.
- **Decided against:** *letting the user type marks into the page* (a second place to
  store things, for what a pencil does; it can be added if asked for); *marking pauses by
  size with words such as "dramatic"* (the app measures a length and does not name an
  intention: science document, section 4).

### F77. Clearing the General Practice history keeps what belongs to a monologue

- **Chosen:** "Clear all history" asks the backend to clear only takes that belong to no
  monologue, and in the page releases only their recordings. A monologue's take that is
  on view, its finished run and its recording in memory are left alone.
- **Why:** the button is on General Practice and the history it clears is General
  Practice's. The store keeps recordings for every screen in one map, so it also keeps a
  note of which ones belong to a monologue.

### F78. Where the voice sits has a section of its own, under "Voice"

- **Chosen:** a separate section, "Where your voice sits", after the Voice section.
- **Why:** the Voice section is about *movement* (how much loudness and pitch vary), and
  every figure in it is relative to the speaker. This is about *where* the voice is,
  against stated ranges, with a table per phrase and its own limits to explain. Mixed
  into the Voice tiles it would have looked like one more variation figure.
- **Decided against:** *a column in the Pace table* (that table is already wide, and is
  about pace); *showing it only when a goal is set* (the user asked for it on every
  recording, and it is a measurement like any other).

### F79. The range is said in words and Hz; the bar is an extra

- **Chosen:** each card states the value, the range with its edges ("Lower range (under
  145 Hz)") and the position in a sentence. The bar under it is hidden from screen
  readers.
- **Why:** the app's rule is that a number comes with what it is. "34%" alone invites
  reading it as "34% masculine"; "34% of the way into it", under the range and its
  edges, cannot be read that way. And a bar with a dot cannot be the only way to learn
  something (the same reasoning as the chart, F25).
- **Decided against:** *a single gauge from "masculine" to "feminine"*: it is the
  picture of the claim the app does not make. *Colour-coding the ranges blue and pink*:
  the same, in colour. The three ranges are drawn in the page's greys, with the mark
  in its one accent colour.

### F80. The words come from one file, the ranges from the result

- **Chosen:** `voiceRange.ts` holds the labels ("Lower range", "Typically heard as a
  masculine voice."). The edges of the ranges are read from `voiceRange.bands` in the
  result on view, never written into the screen.
- **Why:** if the ranges are ever revised, an old result must still show the ranges that
  placed it (the same reasoning as the minimum pause, F58). The labels are few and are
  the screen's wording of three fixed ids, like the stage names.
- **Decided against:** *working the range or the percentage out in the browser from the
  value*: two implementations of one rule. The backend places; the screen displays.

### F81. The goal is remembered in the browser, and belongs to no monologue

- **Chosen:** one `localStorage` key holds the goal last chosen. It applies to every
  recording made in that browser, in General Practice and in Daily Practice, until
  changed. "No goal" removes the key.
- **Why:** a goal is about the speaker, not about a piece. Someone working on their voice
  wants it on every take; someone who is not should never be asked. The backend keeps no
  profile of the user, and the result records the goal it was made with, so nothing is
  lost if the browser forgets.
- **Decided against:** *a setting stored in the backend* (there is no user there to hang
  it on, and B63 explains why a result must keep its own); *asking on every take* (a
  third list to set each time, defaulting to the answer most people never change).

### F82. "Outside your goal" is worked out from the markers the backend sent

- **Chosen:** a phrase is marked when a goal is set, the phrase has a marker, and the
  marker is not the goal's range. "Mixed" and "neutral" count as outside.
- **Why:** it is a comparison of two words the result already carries, so the screen and
  the coaching cannot disagree about a measurement. A phrase that could not be placed is
  not marked and not counted: unknown is not "outside".
- **Honest difference from the coaching:** the coaching counts pitch and resonance
  separately ("2 of 4 phrases stayed in it for pitch"), because each has its own drill.
  The table marks a phrase on the two together. Both are stated on screen in their own
  words; the numbers can differ and both be right.

### F83. The goal list is on the recording forms only

- **Chosen:** General Practice and step 4 of Daily Practice show it. The form that adds
  a monologue's original does not, and there is no way to change the goal of a result
  already made.
- **Why:** the backend ignores a goal on a reference (B66), so offering one would be a
  control that does nothing. And a result is a record: its goal is part of how its
  coaching was written.
- **Honest limit:** "Analyse again" keeps the goal the result already has. To read a
  recording against another goal, the file has to be submitted again with that goal
  chosen.

### Decisions already made for later phases

None. Every phase in the plan is built, and so is everything Phase 6 had listed as left out.
